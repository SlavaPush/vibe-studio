# back-office

Мультиагентный офис, который развивает публичный сервис `vibe-chat` (каталог `apps/chat` монорепозитория [vibe-studio](https://github.com/SlavaPush/vibe-studio)). Офис находится в каталоге `apps/office` того же монорепозитория. Участники ставят задачи по разработке сервиса; фильтр приёма отклоняет посторонние задачи; до трёх задач выполняются одновременно, каждая в отдельном git worktree; пять ролей (исследователь, Supervisor, разработчик, QA, критик) на LangGraph; независимые проверки; агент ревью PR и слияние от GitHub App; очередь выпуска на Render без подтверждения администратора, с проверкой после деплоя, автоматическим откатом и revert-PR.

Для демонстрации офис работает локально. Архитектура допускает деплой на сервер с Docker без переписывания.

## О приложении

Тот же текст показывает раздел «О приложении» в шапке панели. Источник текста в коде — `web/src/lib/about.ts`: при изменении текста обновить модуль и этот раздел. Строка «Модели» изменится на этапе `P5.7`.

Нейроофис — команда AI-агентов, которая развивает чат vibe-chat. Участники ставят задачи, агенты пишут и проверяют код и выпускают новую версию чата.

Что можно делать:

- Поставить задачу по развитию чата. Фильтр приёма отклоняет посторонние и опасные задачи.
- Следить за работой: одновременно выполняются до трёх задач, каждая в отдельной рабочей копии репозитория (git worktree).
- Задачу ведут шесть ролей: исследователь, Supervisor, разработчик, QA, критик и агент ревью PR.
- Подтвердить требования к своей задаче: без подтверждения автора разработка не начинается.
- Код проверяется в изолированном контейнере Docker: lint, тесты и сборка идут без доступа к сети. QA пишет тест Playwright, который не проходит на прежней версии и проходит на новой.
- PR открывает GitHub App офиса. PR сливается только после обязательных проверок CI и одобрения агента ревью PR.
- Очередь выпуска публикует чат на Render и проверяет опубликованную версию. Если проверка не прошла, офис автоматически откатывает чат к прежней версии.

Технологии:

| Область | Технологии |
| --- | --- |
| Интерфейс | React, TypeScript, Vite, shadcn/ui |
| Сервер | FastAPI, LangGraph, Python 3.12 |
| Модели | Anthropic Claude — основной провайдер, OpenAI — резерв; локальная модель Ollama qwen3:8b в профилях local и hybrid |

Подэтап `P4.2` — рабочие копии и sandbox: клон `vibe-chat`, worktree на задачу, политика путей и команд, проверки в Docker, commit кодом офиса, `GET /api/tasks/{id}/diff`. Подэтап `P4.3` — граф ролей LangGraph: шлюз моделей, требования Supervisor и подтверждение владельца, разработчик, проверки, QA и критик, циклы исправления, бюджеты, восстановление после перезапуска. Подэтап `P4.4` — панель на API офиса: вход по коду, стек задач, карточка задачи, постановка задачи, решения по задачам и выпускам, обновление через SSE с восстановлением после разрыва.

## Граф ролей

Задача, занявшая слот, выполняется графом LangGraph (`api/app/graph.py`) в отдельном потоке; одновременно работает не больше трёх графов (`api/app/runner.py`). Порядок узлов:

1. Supervisor готовит требования: краткое описание и до восьми критериев приёмки. При необходимости исследователь загружает до трёх публичных страниц `https` (`api/app/research.py`): адрес сервера проверяется до соединения, соединение идёт на проверенный IP, прокси окружения не используются.
2. Требования записываются в задачу с `spec_hash`, событие `decision_required` ждёт решения `approve_spec`. Граф продолжает только при записи решения в таблице `decisions` для версии из этого события.
3. Разработчик выполняет до шести ходов: чтение, запись и удаление файлов через политику путей, запуск `lint`, `test`, `build`. Commit делает код офиса с trailer `Office-Role` и `Office-Round`. Затем запускается полный набор проверок; при неуспехе задача возвращается разработчику не больше двух раз.
4. QA и критик работают параллельно. QA пишет тест Playwright `apps/chat/web/e2e/office/<task_id>.pw.ts`; тест должен не проходить на `base_sha` утверждением `expect` и проходить на версии задачи. Backend `vibe-chat` в sandbox недоступен, поэтому тест до `page.goto` вызывает `mockApi(page, overrides?)` из `apps/chat/web/e2e/office/support/mock-api.ts` (раздел «Подмена API для тестов QA»); пути контракта, клиента API, примеров ответов и этого модуля QA получает в контексте. Промпт QA требует локаторы по роли и точному имени (`{ exact: true }`) или `getByLabel` с точным текстом и ожидание состояния через `expect`. Результат определяется по JSON-отчёту Playwright (`parse_playwright` в `api/app/sandbox.py`):
   - `passed` и `failed` — тест прошёл или не прошёл на утверждении `expect`;
   - `test_error` — ошибка теста до утверждения: ошибка локатора, `strict mode violation`, таймаут действия или теста, исключение в коде теста; файл теста указан в `location` ошибки или в её стеке. Сообщение Playwright (без ANSI, до 1500 символов) и строка передаются QA;
   - `invalid` — тест обратился к API без подмены;
   - `no_evidence` — нет отчёта, глобальная ошибка Playwright, тест пропущен или прерван, не запустился браузер или сервер приложения, таймаут fixture, ошибка вне файла теста. Набор повторяется один раз (`INFRA_RETRIES`), затем задача получает `needs_attention` («Нет свидетельства QA»).

   QA получает до трёх попыток (`QA_ATTEMPTS`) в каждом цикле исправления. Следующая попытка получает обратную связь: тест прошёл на исходной версии; `test_error` на исходной версии или на версии задачи (текст ошибки, строка, подсказка исправить тест); список запросов без подмены. Если тест не проходит утверждением на версии задачи, QA один раз в цикле проверяет свой тест с сообщением утверждения: изменённый тест проверяется заново на обеих версиях, тест без изменений даёт блокирующее замечание разработчику. Повторное падение утверждением после исправления теста тоже даёт замечание разработчику. После третьей неудачной попытки задача получает `needs_attention` с последней причиной. Состояние попытки QA (номер, фаза, обратная связь, хеш файла теста до попытки, ответ модели, `qa_sha`) записывается атомарно в артефакт `qa-state-<attempt>-<dev_round>.json` до вызова модели, после ответа, после commit и после проверок; после перезапуска граф продолжает ту же попытку: без повторного вызова модели, если ответ уже получен, и без повторного commit. Commit QA получает trailer `Office-Round: <attempt>-<dev_round>-<попытка QA>`. Критик проверяет diff по требованиям.
5. Блокирующее замечание возвращает задачу разработчику (не больше двух циклов, `fix_cycles`), затем `needs_attention`. Без блокирующих замечаний офис повторно проверяет всю ветку `base_sha..HEAD` (раздел «Повторная проверка ветки»); при нарушении задача получает `needs_attention` с причиной, иначе переходит в `awaiting_integration` и освобождает слот. Дальше задачу ведёт исполнитель выпуска (раздел «PR офиса»).

Ответ модели — JSON по схеме роли; ответ вне схемы или обрезанный пределом выходных токенов не исполняется, задача получает `failed` с отдельной причиной для каждого случая. Поле `step` действия — перечисление шагов роли из `policies/commands.yaml`: у разработчика `lint`, `test`, `build` и `api-test` (только задача `backend_api`, pytest API в песочнице Python), у QA только `e2e`. Промпты Supervisor, разработчика, QA и критика выбираются по классу задачи. В схемах ходов длинные текстовые поля идут последними: `actions` — последнее поле ответа, `content` — последнее поле действия. При другом порядке `qwen3:8b` в части ответов продолжала поле `content` строками комментариев до предела токенов. Каждое обращение к модели, включая резервного провайдера, учитывается в `usage` до вызова; после 30 обращений задача получает `needs_attention`. Предел времени задачи — `OFFICE_TASK_TIME_LIMIT_MINUTES` (по умолчанию 60) от перехода в `developing`. Обращения к Ollama выполняются по одному.

Checkpoint графа хранится в `<имя БД>.checkpoints.sqlite` рядом с SQLite-файлом офиса или в той же БД PostgreSQL. После перезапуска API продолжает графы задач в статусах `awaiting_spec_approval`, `developing`, `reviewing`. Выход задачи из статусов слота (`cancel`, `needs_attention`, `failed`) останавливает граф и удаляет контейнеры задачи; worktree отменённой задачи удаляется после остановки графа. Контейнеры проверок помечаются меткой `back-office.workspace=<хеш каталога рабочей области>`; при старте API удаляет контейнеры с этой меткой, оставшиеся от прежнего процесса. `retry` начинает новую попытку с сохранёнными требованиями, worktree, `usage` и `fix_cycles`; требования подтверждаются заново.

## Рабочая область и sandbox

Офис держит клон монорепозитория `TARGET_REPO_URL` (`vibe-studio`) в `<WORKSPACE_DIR>/vibe-studio` (по умолчанию `apps/office/workspace/`). Целевое приложение — каталог `apps/chat`. Задача, занявшая слот, получает worktree `<WORKSPACE_DIR>/wt/<task_id>` на ветке `office/<task_id>` от `origin/main`; `branch` и `base_sha` записываются в задачу. Worktree создаётся со sparse checkout в режиме cone только для `apps/chat/`: каталогов `apps/office/` и `.github/` в нём нет, файлы корня монорепозитория (`README.md`, `LICENSE`) присутствуют, запись в них запрещена политикой. Настройка sparse checkout хранится в конфигурации самого worktree и не действует на клон и другие worktree. Если после перезапуска найден worktree без sparse checkout, офис включает его на месте и сохраняет изменения в `apps/chat/`; если в worktree есть изменения вне `apps/chat/`, worktree не меняется, задача получает `needs_attention`. Политику путей и свой код офис читает только из собственного checkout (`apps/office/policies/`), никогда из клона или worktree задачи. Рабочая область прежнего репозитория `vibe-chat` не подходит: для `vibe-studio` задайте новый `WORKSPACE_DIR` или очистите `workspace/` и используйте новую БД офиса. Отмена и выпуск удаляют worktree, ветка остаётся. При `failed` и `needs_attention` worktree сохраняется, `retry` использует его повторно. Задача в `awaiting_integration` и следующих статусах слот не занимает, но worktree сохраняет. При старте API создаёт недостающие worktree незакрытых задач, которым они нужны (от `awaiting_spec_approval` до `deploying`, а также `failed` и `needs_attention`), и удаляет worktree отменённых и выпущенных задач. Без `TARGET_REPO_URL` API не запускается.

`policies/paths.yaml` задаёт пути относительно корня монорепозитория, которые роли читают и пишут, по классу задачи (`frontend_ui` или `backend_api`, раздел «Серверный контур»). Задача `frontend_ui`: разработчик — `apps/chat/web/src/**`, `apps/chat/web/public/**`, `apps/chat/web/index.html`, кроме серверной зоны (`src/api/**`, `src/mocks/**`, `ModelSelector.tsx`); QA — только `apps/chat/web/e2e/office/**/*.pw.ts`. Задача `backend_api`: разработчик — дополнительно `apps/chat/api/app/**` (`.py`, `.sql`), `apps/chat/api/pyproject.toml`, `apps/chat/contracts/**` (`.md`), `src/api`, `src/mocks`, `apps/chat/web/package.json`, `ModelSelector.tsx` и существующие тесты чата (`apps/chat/api/tests/**` кроме `tests/office/`, `*.test.*`, `apps/chat/web/src/test/**`, `apps/chat/web/e2e/office/support/**`); QA — только `apps/chat/api/tests/office/test_*.py`. Lock-файлы `package-lock.json` и `uv.lock` пишет только шаг офиса (писатель «офис», до 2 МиБ). Запись в `apps/office/**`, `.github/**`, `apps/chat/infra/**`, `apps/chat/api/scripts/**`, корневые файлы, файлы окружения, Dockerfile, конфигурации сборки и `*.spec.*` запрещена обоим классам; тесты QA разработчику обоих классов недоступны. Запреты общего списка и серверная зона действуют без учёта регистра. Symlink в любом компоненте пути, `..`, абсолютные пути, недопустимые расширения и файлы больше 200 КБ отклоняются. Каждый вызов инструмента пишет событие `tool_called`. Commit выполняет код офиса: каждый изменённый путь проверяется повторно, исполняемые файлы, symlink и submodule отклоняются.

`policies/commands.yaml` задаёт шаги проверок `install`, `lint`, `test`, `build`, `e2e`, их таймауты, роли и пределы контейнера. Контейнер запускается от пользователя `10001` с `--cap-drop ALL`, `no-new-privileges`, корневой файловой системой только для чтения, пределами памяти, CPU и процессов и без сети (кроме `install`). Каталог `apps/chat` worktree монтируется в контейнер как `/src` только для чтения, поэтому пути внутри sandbox заданы относительно `apps/chat`. Зависимости ставятся `npm ci` в том Docker `office-nm-<хеш lock-файла>`, общий для задач с одинаковым `apps/chat/web/package-lock.json`. Шаг `e2e` собирает приложение (ошибка сборки — код выхода 90), раздаёт `web/dist` сервером `docker/sandbox/office-e2e/serve.mjs` и запускает тесты QA `apps/chat/web/e2e/office/**/*.pw.ts` в Playwright. Сервер отвечает на неподменённые запросы к `/api/` и `/healthz` ошибкой `501 office_unmocked_api` и записывает их в артефакт `unmocked-api.txt`. JSON-отчёт `playwright-report.json` сохраняется в артефактах. Одновременно работает не больше `OFFICE_SANDBOX_CONTAINERS` контейнеров. Журналы шагов, скриншоты и трассы доступны через `GET /api/tasks/{id}/artifacts/{name}`.

### Подмена API для тестов QA

Модуль `apps/chat/web/e2e/office/support/mock-api.ts` экспортирует `mockApi(page, overrides?)` и `fixtures`. `mockApi` регистрирует `page.route("**/api/**")` и отвечает без обращения к серверу по контракту `apps/chat/contracts/api.md`: `GET /api/me`, `POST /api/demo-session`, `GET /api/models`, `GET /api/version` (`dev`, как в сборке без версии), `GET /api/conversations` (один диалог `fixtures.conversation` с названием «Тестовый диалог QA»), `POST /api/conversations`, `PATCH /api/conversations/{id}`, `GET /api/conversations/{id}/messages` (пустая история), `POST /api/conversations/{id}/runs` (задание `queued`), `GET /api/runs/{id}/events` (поток `text/event-stream` до события `completed` с ответом `fixtures.reply`), `GET /api/runs/{id}` (завершённое задание). Неподменённый путь получает `404 not_found` в формате ошибки контракта. `overrides` задаёт ответ по ключу `"<METHOD> <путь>"`, в пути допустимы параметры `{id}`; значение — `{ status?, body?, contentType?, headers? }` или функция запроса, возвращающая такой ответ. Тест vitest `support/mock-api.test.ts` (запускается `npm run test` приложения чата) сверяет ответы модуля с примерами контракта `src/mocks/contract-examples.ts`; при изменении контракта модуль обновляется вместе с ним. `export_qa` переносит весь каталог `e2e/office` в `/qa`, поэтому импорт `./support/mock-api` работает в sandbox, в критическом E2E итогового commit и в Docker-тестах CI `office-sandbox`. QA модуль не пишет: QA пишет только `*.pw.ts`. Каталог `support/` входит в серверную зону: модуль и его тест изменяет только разработчик задачи `backend_api`, PR такой задачи ждёт одобрения владельца.

Образ sandbox собирается вручную из корня монорепозитория (без образа шаги завершаются ошибкой «Sandbox недоступен»):

```bash
docker build -t back-office-sandbox:p4 apps/office/docker/sandbox
```

Задачи серверного контура дополнительно требуют образ песочницы Python (тесты API, `api-compat`, шаг `uv lock`) и PostgreSQL. После изменения `docker/sandbox-python/step.sh` образ пересобирается:

```bash
docker build -t office-python-sandbox:p5 apps/office/docker/sandbox-python
docker pull postgres:16-alpine
```

## Серверный контур

С этапа `P5.4` офис принимает задачи по серверу чата: API, контракт, схема БД, зависимости, выбор моделей, маршрутизация, уровни усилий и лимиты (класс `backend_api`). Офис, CI, инфраструктура, Dockerfile и `.env*` по-прежнему не изменяются.

- Контур задачи (`ui` или `server`) определяется по путям diff: хотя бы один файл серверной зоны — `server`. Карточка задачи в панели показывает контур.
- Изменённый разработчиком манифест (`package.json` или `pyproject.toml`, только разделы зависимостей) получает согласованный lock-файл: офис выполняет `npm install --package-lock-only` или `uv lock` в песочнице с сетью и фиксирует его commit с trailer `Office-Role: office`.
- Схема БД меняется только добавочно (новые таблицы, колонки без `NOT NULL`, индексы); тест `api-compat` прогоняет pytest базовой версии на новой схеме.
- Серверная задача проверяется `pytest` API в песочнице Python с PostgreSQL без интернета; QA пишет тест `apps/chat/api/tests/office/test_<task_id>.py`.
- Существующие тесты чата (`apps/chat/api/tests/**`, `*.test.*`, `apps/chat/web/src/test/**`, `apps/chat/web/e2e/office/support/**`) входят в серверную зону (решение владельца 25 октября 2026): их изменяет и удаляет только разработчик задачи `backend_api`, когда требования меняют закреплённое тестами поведение (например, каталог моделей). Тесты QA разработчику недоступны. Сводка для владельца в описании PR перечисляет изменённые и удалённые тесты.
- PR серверного контура сливается только после одобрения владельца (`APPROVED` от `OFFICE_OWNER_LOGIN` для текущего head). Агент ревью PR готовит сводку для владельца, офис записывает её в описание PR. «Request changes» закрывает PR, задача получает `failed` (`owner_rejected`) с комментарием владельца. То же для revert-PR и доработки серверного изменения.

Подробности — раздел «Серверный контур» `contracts/integrations.md`.

## PR офиса

Задачу в `awaiting_integration` ведёт исполнитель выпуска (`api/app/release.py`) — один поток API:

1. Повторно проверяет ветку и отправляет `office/<task_id>` в `OFFICE_GITHUB_REPO` (по умолчанию `SlavaPush/vibe-studio`) по HTTPS с токеном установки GitHub App.
2. Ищет открытый PR ветки и, если его нет, открывает PR в `main`. Номер, адрес PR и отправленный SHA сохраняются в задаче (`pr_number`, `pr_url`, `head_sha`).
3. Читает запуски GitHub Actions для head PR и сохраняет сводку обязательных проверок ruleset `main` в поле задачи `checks` (событие `checks_status`). Провал обязательной проверки закрывает PR, задача получает `failed` с `failure_kind = checks_failed`, повтор запрещён. Проверки не завершились за `OFFICE_CHECKS_TIMEOUT_MINUTES` — `needs_attention`.
4. Все проверки `success` и повторная проверка ветки пройдена — вызывает агента ревью PR (роль `pr_reviewer`). Решение (`approve` или `reject`, обоснование, что изменить, чек-лист) сохраняется для head PR в таблице `pr_reviews` и в поле задачи `pr_review`. Невалидный ответ или ошибка модели — `needs_attention`, PR открыт. `reject` закрывает PR, задача получает `failed` с `failure_kind = pr_rejected`.
5. `approve` в контуре `server` — офис записывает сводку для владельца в описание PR и ждёт отзыв владельца на GitHub без ограничения времени (раздел «Серверный контур»).
6. `approve` в контуре `ui` или одобрение владельца в контуре `server` — сливает PR в `main` (squash) запросом от GitHub App с `sha` проверенного head. Изменённый head — решение недействительно, `needs_attention`. Таймаут слияния — только сверка с GitHub, без повторного запроса. Итоговый commit сохраняется в `merge_sha`.
7. Ждёт обязательных проверок `ci.yml` события `push` для `merge_sha` и выполняет в sandbox критический E2E на этом commit (`lint`, `test`, `build`, `e2e` со всеми тестами QA из `main`; при изменении сервера — также `api-test` и `api-compat`). Провал — `failed` (`checks_failed`).
8. Создаёт кандидата выпуска с основанием — опубликованной версией сервиса (`OFFICE_SERVICE_URL`/`api/version`); задача переходит в `awaiting_release`. Пока идёт выпуск, кандидат не создаётся.
9. Отмена задачи до слияния закрывает её PR. После слияния и во время слияния отмена недоступна.

Каждое изменяющее действие записывается в журнал операций до вызова и сверяется с GitHub после перезапуска или потерянного ответа (раздел «Журнал операций» `contracts/integrations.md`). Неустановленный исход переводит задачу в `needs_attention`; `retry` возвращает её в `awaiting_integration` и продолжает с места остановки.

## Очередь выпуска

Тот же поток после задач ведёт очередь выпуска (`api/app/release_queue.py`, Render — `api/app/render.py`, проверка сервиса — `api/app/service_check.py`). Подтверждения выпуска администратором нет.

1. Одновременно выполняется один выпуск. Откаты деплоятся первыми; из обычных кандидатов выбирается самый новый по истории `main`, его предки получают `superseded` и публикуются в его составе.
2. Перед деплоем офис согласует опубликованную версию (в том числе деплой вне офиса), сверяет основание кандидата (расхождение — `revoked` и новый кандидат того же commit), ждёт чужой деплой Render и проверяет происхождение каждого commit выпуска: PR офиса, PR или прямой push логина из `OFFICE_TRUSTED_GITHUB_LOGINS`.
3. Деплой — `POST /v1/services/{id}/deploys` с `commitId`, опрос до терминального статуса. Ошибка деплоя — `failed` без отката.
4. Проверка после деплоя — `/healthz`, `/api/version` и `<meta name="app-version">` главной страницы в пределах `OFFICE_VERIFY_SECONDS`. Успех — `released`.
5. Неуспех — один автоматический откат Render rollback к прежней сборке и его проверка. Успех отката — кандидат и задача `failed` (`verify_failed`), выпуск блокируется (`release_blocked_by`), офис сам создаёт revert-PR `office/revert-<release_id>` от App с обычными проверками и агентом ревью; revert отменяет только слияния PR офиса из диапазона выпуска, commit владельца остаются. Публикация revert-commit снимает блокировку. Конфликт revert, отказ или отсутствие слияний офиса в диапазоне — `needs_attention`: администратор повторяет revert-PR решением `resume_releases` без `fix_sha` или владелец исправляет `main` и вызывает `resume_releases` с `fix_sha`.
6. Неустановленный исход деплоя или отката, ошибка отката, деплой вне офиса во время выпуска — `needs_attention`, очередь занята. Повторного запроса к Render нет; продолжение — `resume_releases` администратора после сверки с Render и сервисом.
7. Непрошедшие обязательные проверки `push` (`conclusion = failure`) или критический E2E итогового commit слияния офиса — задача `failed` (`checks_failed`), выпуск блокируется, revert-PR тем же механизмом без Render rollback. Ручной откат администратора (необязательная причина до 500 символов) переводит задачи откатанного выпуска в `failed` (`rolled_back`). Блокировка одна: новые сбои добавляют слияния в её набор отмены, блокировку снимает только публикация кандидата с revert-commit всех попыток набора.

Доработка после отката: после публикации revert офис возвращает задачи отменённых слияний на доработку — один раз (`OFFICE_REWORK_LIMIT`). Задача занимает первый свободный слот раньше обычной очереди, сразу в `developing` без повторного подтверждения требований, на ветке `office/<task_id>-r1` от текущего `main` с исходным изменением (`cherry-pick`; при конфликте — чистый `main`). Разработчик получает причину отката, события деплоя, выдержки логов Render и упавшей job GitHub Actions и исходный diff — как данные, после очистки от секретов и персональных данных, каждый источник до 4 КБ. Повторный сбой после доработки — только revert, причина «Лимит доработки исчерпан». Подробности — раздел «Доработка после отката» `contracts/integrations.md`.

Ручная проверка отката на реальном сервисе: `OFFICE_VERIFY_FAULT=1` заставляет проверку выпуска задачи считаться неуспешной (в журнале — `fault = true`); проверка отката и кандидатов исправления (revert-PR, `fix_sha`) выполняется реально. После проверки переменную очистить.

## Повторная проверка ветки

Перед переходом задачи в `awaiting_integration` офис проверяет всю ветку `base_sha..HEAD` функцией `api/app/branch_check.py`, независимо от проверок отдельных commit:

- каждый изменённый или удалённый путь допустим для одной из ролей класса задачи политики `policies/paths.yaml`;
- `package.json` и `pyproject.toml` изменены только в разделах зависимостей, `schema.sql` — только добавочно;
- режим файла — обычный файл `100644`; исполняемые файлы, symlink и submodule отклоняются;
- содержимое, которое git считает двоичным (в том числе с байтом NUL), отклоняется;
- добавленные строки не содержат комментариев отключения проверок `eslint-disable`, `oxlint-disable`, `@ts-ignore`, `@ts-nocheck`, `@ts-expect-error`. Строки берутся из `git diff --text`, поэтому признак двоичного файла их не скрывает.

Нарушение переводит задачу в `needs_attention`: событие `tool_called` с инструментом `verify_branch` содержит перечень нарушений, PR не создаётся. Исполнитель выпуска вызывает ту же функцию перед каждым push ветки задачи.

Та же функция работает в обязательной проверке GitHub `office-paths` (`.github/workflows/office-paths.yml`, событие `pull_request_target`, только ветки `office/*`). Workflow берёт checkout базовой ветки без `ref` и с `persist-credentials: false`, получает объекты head PR через `git fetch` только как данные и запускает скрипт офиса из базовой ревизии. Права — `contents: read`, секретов нет. Скрипт можно запустить локально:

```bash
cd apps/office/api && uv run python -m scripts.check_branch --repo ../../.. --base <sha базы> --head <sha ветки>
```

Код возврата 0 — нарушений нет, 1 — есть нарушения или проверка не выполнена. Diff считается от merge-base базового commit и ветки. Повторная проверка офиса применяет права класса задачи; `office-paths` и revert-PR — права любого класса. Обе проверяют также разделы манифестов зависимостей и добавочность `apps/chat/api/app/schema.sql`.

Панель работает с API офиса. Без сеанса она показывает вход по личному коду участника (раздел «Вход по личному коду»); участник после входа и после перезагрузки страницы определяется через `GET /api/me`. Задачи, слоты, выпуски и состояние очереди выпуска (`GET /api/release-queue`) загружаются из API и обновляются по потоку `GET /api/events`; события выпуска (`release_candidate`, `deploy_status`, `rollback_status`, `release_blocked`, `release_unblocked`, `external_publish`) перечитывают выпуски и очередь. После разрыва потока панель перечитывает задачи, выпуски и слоты, затем переподключается с паузами 1, 2, 5 и 10 секунд. Карточка задачи читает журнал из `GET /api/tasks/{id}/events`, пока открыта вкладка «Ход работы». Решения отправляются с `expected_version` и `idempotency_key`; отмена задачи, откат и возобновление остановленного выпуска требуют подтверждения в диалоге. Очередь выпуска показывает проверку после деплоя, результат отката, блокировку после отката с revert-PR и форму `resume_releases` с `fix_sha` для администратора, а при revert-PR, требующем внимания, — кнопку «Повторить revert-PR» (`resume_releases` без `fix_sha`); без Render — предупреждение «Выпуск не настроен». Форма ручного отката содержит необязательное поле «Причина отката» (до 500 символов), причина показывается у кандидата. Карточка задачи на доработке показывает «Доработка после отката: попытка N из M» и причину отката с комментарием администратора. Ответ `401 unauthorized` от любой операции возвращает экран входа. Кнопка «Выйти» в шапке после подтверждения в диалоге вызывает `DELETE /api/office-session`: сервер удаляет сеанс и cookie, панель закрывает потоки и показывает экран входа. Войти снова тем же кодом нельзя, для нового входа нужен новый код. Потоки SSE удалённого или истёкшего сеанса сервер завершает не позже следующего `: ping`. Если `GET /api/me` отвечает ошибкой, отличной от `401` (например, `503 codes_unavailable` или сбой сети), панель не показывает форму входа: она показывает сообщение и кнопку «Проверить сеанс снова», которая повторяет только `GET /api/me`. Тестовые данные `mocks/` используются только в vitest.

## Вход по личному коду

У каждого участника один личный одноразовый код для чата и офиса. Реестр кодов — таблица `access_codes` чата в Supabase. Коды создаёт владелец скриптом чата `apps/chat/api/scripts/access_codes.py` (`apps/chat/README.md`, раздел «Коды доступа»):

- `add <метка> --office-role participant` или `--office-role admin` создаёт код с ролью офиса. Без `--office-role` код открывает только чат.
- `office-role <метка> participant|admin|none` задаёт или снимает роль офиса у выданного кода. Так участник с кодом, выданным до `P5.6`, получает вход в офис без нового кода.
- `revoke <метка>` закрывает код в обоих интерфейсах.

Правила входа:

- Один код даёт один вход в чат (`used_at`) и один вход в офис (`office_used_at`). Вход в чат не расходует вход в офис, и наоборот.
- Роль офиса и отображаемое имя участника берутся из кода: `office_role` и метка. Метка показывается полностью и служит именем автора задачи в панели. Каждый вход создаёт нового участника офиса.
- Повторный вход тем же кодом, отозванный код и код без роли получают `401 invalid_access_code`. Попытка входа кодом без роли код не расходует.
- Роль фиксируется при входе. Изменение `office_role` после входа на действующий сеанс не влияет; для немедленного закрытия доступа служит `revoke`.
- Сеанс действует 7 дней. Выход («Выйти») расходует вход: войти снова тем же кодом нельзя. После удаления cookie или на другом устройстве участнику нужен новый код.
- Отзыв закрывает сеансы офиса этого кода. Обычный запрос получает `401 unauthorized` не позже чем через 10 секунд (результат проверки кода кешируется на `Settings.codes_check_seconds`). Открытый поток SSE проверяет сеанс перед каждым `: ping` (`Settings.sse_ping_seconds`, 15 секунд), поэтому завершается не позже чем через 25 секунд и время запроса к реестру.
- Без `OFFICE_CODES_DATABASE_URL` или при недоступном реестре вход и проверка сеанса получают `503 codes_unavailable`, открытые потоки SSE завершаются. Остальной API запускается, `/api/health` доступен. Ответ `503` не считается неверной попыткой для предела входа.
- Если офис отметил `office_used_at`, но не создал сеанс (сбой БД офиса или обрыв связи), код считается использованным. Автоматического повтора нет. Владелец выдаёт новый код или вручную снимает отметку: `UPDATE access_codes SET office_used_at = NULL WHERE label = '<метка>'` в Supabase SQL Editor.
- Задача принадлежит участнику, который её поставил. Новый вход, даже того же человека с новым кодом, создаёт другого участника, и прежние задачи ему не принадлежат. Подтвердить требования, отменить или повторить задачу может только её автор; администратор может только повторить задачу в `needs_attention` на этапе интеграции. Чтобы передать задачу новому участнику, владелец выполняет в БД офиса `UPDATE tasks SET owner_id = '<id участника>' WHERE id = '<id задачи>'`. `id` участника — поле `id` ответа `GET /api/me` в его сеансе.

Переход с общих кодов офиса. Сеансы, созданные по общим кодам офиса до `P5.6`, после обновления недействительны: у их участников нет `access_code_id`. Перед переходом завершите или отмените старой сборкой все незавершённые задачи прежних участников в статусах `queued`, `awaiting_spec_approval`, `developing`, `reviewing` и `needs_attention`. Задачи `queued` при старте новой сборки переходят в `awaiting_spec_approval` и занимают слоты. Задачу `failed` отменить нельзя: окончательно завершившиеся задачи остаются историей, а задачу для повтора передайте новому участнику. Задачи, не завершённые до перехода, передайте новым участникам запросом из предыдущего пункта: иначе задачи в статусах слота занимают слоты, а отменить их некому.

`OFFICE_CODES_DATABASE_URL` — строка подключения session pooler Supabase. Подходит строка `DATABASE_URL_SUPABASE` чата. Офис держит не больше двух соединений и обращается только к таблице `access_codes`: отметка `office_used_at` и проверка `revoked_at`. Схему чата офис не применяет: колонки `office_used_at` и `office_role` добавляет `apps/chat/api/app/schema.sql` при старте чата или при запуске скрипта кодов.

Необязательный шаг владельца: отдельная роль БД с правами только на нужные колонки. В Supabase SQL Editor:

```sql
CREATE ROLE office_codes LOGIN PASSWORD '<пароль>';
GRANT USAGE ON SCHEMA public TO office_codes;
GRANT SELECT (id, label, code_hash, revoked_at, office_role, office_used_at), UPDATE (office_used_at) ON access_codes TO office_codes;
CREATE POLICY office_codes_select ON access_codes FOR SELECT TO office_codes USING (true);
CREATE POLICY office_codes_update ON access_codes FOR UPDATE TO office_codes USING (true) WITH CHECK (true);
```

Затем в `OFFICE_CODES_DATABASE_URL` указать строку session pooler с пользователем `office_codes.<project_ref>` и этим паролем. Роль и политики в `schema.sql` чата не добавляются: локальные и тестовые БД такой роли не имеют.

## Профили моделей

`policies/models.yaml` задаёт модель и уровень усилий для каждой роли в профилях `local` (Ollama), `cloud` (Anthropic с резервом OpenAI) и `hybrid` (локальная модель для Supervisor и исследователя, облачная для разработчика, QA, критика и фильтра приёма). QA в `cloud` — `claude-sonnet-5-5` с усилием `high` и резервом `gpt-6.1-sol`, в `hybrid` — `claude-haiku-5-5` с усилием `low` и резервом `gpt-6-luna` (`P5.2a`: в ручных проверках `P5.1` и `P5.2` тест QA на Haiku с `low` в профиле `cloud` падал из-за ошибок локаторов). Раздел `capabilities` описывает параметр рассуждения каждой пары провайдер/модель; поле `verified` и список `verified_values` заполняются после реального вызова (smoke-проверки этапа `P0`). Код читает файл начиная с этапа `P4`.

Локальные ограничения: одна загруженная модель Ollama, основная модель `qwen3:8b`, один запрос к модели одновременно (`local_limits` в `policies/models.yaml`). Шлюз офиса сам отправляет запросы к Ollama по одному. Сервер Ollama настраивается двумя переменными окружения:

- `OLLAMA_NUM_PARALLEL=1` — сервер обрабатывает один запрос к модели одновременно, как семафор шлюза;
- `OLLAMA_MAX_LOADED_MODELS=1` — в памяти держится не больше одной модели. Если появится вторая модель (например, `llama3.1:8b`), сервер выгрузит первую, а не займёт ещё около 10 GB из 16 GB памяти машины.

Приложение Ollama на macOS читает переменные окружения через `launchctl`. Задать переменные, затем закрыть Ollama в строке меню и запустить заново:

```bash
launchctl setenv OLLAMA_MAX_LOADED_MODELS 1
launchctl setenv OLLAMA_NUM_PARALLEL 1
```

Значения, заданные `launchctl setenv`, действуют до перезагрузки macOS; после перезагрузки команды выполняются снова. Проверка: обе команды печатают `1`, а `ollama ps` во время работы офиса показывает одну модель:

```bash
launchctl getenv OLLAMA_MAX_LOADED_MODELS
launchctl getenv OLLAMA_NUM_PARALLEL
ollama ps
```

Скрипт замера `api/scripts/measure_local.py` перед вызовами печатает загруженные модели (`GET /api/ps`) и предупреждает, если их больше одной.

Docker Desktop на машине владельца ограничен 8 GB памяти. Одновременно запускать не больше одного-двух контейнеров проверок при загруженной локальной модели.

## Скорость профиля `local`

Скрипт `api/scripts/measure_local.py` вызывает `qwen3:8b` через шлюз офиса (`ModelsGateway.call_provider`) с маршрутами профиля `local`, системными промптами и схемами ролей и сборщиком контекста `assemble` с бюджетом роли. БД задач не нужна, облачные модели не вызываются: шаг, маршрут которого в профиле `local` ведёт не в Ollama, не запускается. Входные данные фиксированы и повторяют контекст графа для небольшой задачи интерфейса (счётчик символов под полем ввода):

| Шаг | Схема | `think` | Контекст |
| --- | --- | --- | --- |
| `supervisor/specify` | `SpecDraft` | нет | текст задачи, листинг `apps/chat/web/src` (42 пути) |
| `developer/implement` | `Turn` | да | требования, листинг, второй ход разработчика с прочитанным компонентом TSX (143 строки) |
| `qa/qa` | `QaTurn` | нет | требования, путь теста QA, листинг |
| `critic/review` | `CriticReview` | да | требования, отчёт проверок, diff (73 строки) |

```bash
cd api && PYTHONPATH=. uv run python scripts/measure_local.py --runs 3
```

Скрипт печатает строку на вызов (время, `prompt_eval_count`, `eval_count`, токенов в секунду по `eval_duration`, время загрузки модели, `done_reason`, соответствие схеме) и сводку по шагу. Код возврата 1, если хотя бы один ответ не прошёл схему или вызов не удался; остальные вызовы при этом выполняются.

Замер 24 октября 2026 на MacBook Pro M1 Pro 16 GB, Ollama 0.40.7, `qwen3:8b` (в памяти 9.9 GB при `num_ctx` 32768, 100% GPU), по 3 вызова на шаг, модель уже загружена. Все 12 ответов завершились с `done_reason` `stop` и прошли схему.

| Шаг | Медиана, с | Мин–макс, с | Вход, токенов | Выход, токенов | Токенов/с |
| --- | --- | --- | --- | --- | --- |
| `supervisor/specify` | 19.8 | 19.1–22.5 | 788 | 319 | 20.8 |
| `developer/implement` | 111.6 | 100.6–132.0 | 2130 | 2049 | 19.9 |
| `qa/qa` | 29.5 | 27.2–33.6 | 1051 | 506 | 21.0 |
| `critic/review` | 31.5 | 29.8–35.2 | 1459 | 516 | 20.9 |

Скорость генерации стабильна (около 20 токенов в секунду), поэтому время вызова определяется числом выходных токенов. У разработчика и критика с `think` большую часть выхода занимает рассуждение. Загрузка модели в память перед первым вызовом — около 18 с (в замер не входит).

Оценка времени шагов одной задачи без циклов исправления. Оценка шага равна медиане вызова, умноженной на типовое число вызовов шага в графе. Допущения:

- Supervisor — 1 вызов, разработчик — от 2 до 6 ходов (предел `DEV_TURNS`), QA — от 1 до 3 ходов (`QA_TURNS`), критик — 1 вызов. Время ходов разработчика взято по второму ходу; запись большого файла увеличивает выход хода.
- Проверки sandbox: набор `verify` и два набора со свидетельством QA вместе — около 60 с. Источник — Docker-тесты `P4.2`–`P4.3`: тест sandbox с тремя наборами — 59 с вместе с клоном и `npm ci`, оба Docker-теста — 122 с. Шаги `lint`, `test`, `build` внутри ходов разработчика не учтены.
- Обращения к Ollama выполняются по одному на весь офис, поэтому в профиле `local` QA и критик работают последовательно, а три задачи в слотах ждут друг друга на каждом вызове модели.

| Шаг задачи | `local` | `hybrid` |
| --- | --- | --- |
| Требования (Supervisor) | 20 с | 20 с (`qwen3:8b`) |
| Разработчик | 3.7–11.2 мин | Sonnet, локальный замер не применим |
| `verify` | около 20 с | около 20 с |
| QA и критик | 1.7–2.7 мин (QA 0.5–1.5 мин + критик 0.5 мин + свидетельство QA около 40 с) | QA на Haiku + свидетельство около 40 с параллельно с критиком на Sonnet |
| Итого одна задача | 6–15 мин | около 1.3 мин на `qwen3:8b` и sandbox плюс время облачных моделей |

В профиле `local` три одновременные задачи делят одну модель: время вызовов модели суммируется (5–13.5 мин на задачу), и проход трёх задач занимает около 15–40 мин. Каждый цикл исправления повторяет разработчика, `verify`, QA и критика. Предел `OFFICE_TASK_TIME_LIMIT_MINUTES` (60 мин от перехода в `developing`) включает ожидание модели, поэтому при трёх задачах `local` и циклах исправления задача может получить `needs_attention` по времени. Профиль `hybrid` выносит разработчика, QA и критика в облако. Оценка `hybrid` сверяется с интервалами событий ручного сценария `P4`.

## Запуск локально

Требования: Python 3.12 и [uv](https://docs.astral.sh/uv/), Node 24, Docker, [Ollama](https://ollama.com) с моделью `qwen3:8b`.

```bash
cp .env.example .env
```

```bash
ollama pull qwen3:8b
```

API офиса на `127.0.0.1:8001` (переменные читаются из `../.env`; без `OFFICE_CODES_DATABASE_URL` вход невозможен, раздел «Вход по личному коду»):

```bash
cd api && uv sync && uv run --env-file ../.env uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8001
```

Состояние офиса хранится в `OFFICE_DATABASE_URL` (по умолчанию `api/office.sqlite`). Схема `api/app/schema.sql` применяется при старте. Фильтр приёма читает `policies/intake.yaml` (запрещённые пути и команды) и профиль `intake_filter` из `policies/models.yaml`.

Панель на `http://localhost:5173` (dev-сервер Vite проксирует `/api` на `127.0.0.1:8001` без замены заголовков `Host` и `Origin`):

```bash
cd web && npm ci && npm run dev
```

Открывать панель нужно по `http://localhost:5173`, а не по `http://127.0.0.1:5173`. Cookie сеанса имеет атрибут `Secure`; Chrome принимает такие cookie по HTTP только для `localhost`.

Проверки из корня монорепозитория (те же команды выполняют job `office-api`, `office-web` и `office-sandbox` корневого `.github/workflows/full.yml`, который запускается только вручную):

```bash
(cd apps/office/api && uv sync --locked && uv run pytest)
(cd apps/office/web && npm ci && npm run lint && npm run test && npm run build)
docker build -t back-office-sandbox:p4 apps/office/docker/sandbox
docker run --rm -v "$PWD/apps/chat/web:/src:ro" -v "$PWD/apps/chat/contracts:/work/contracts:ro" back-office-sandbox:p4 sandbox-smoke /src
```

Тесты БД выполняются на SQLite и, при заданной `OFFICE_TEST_POSTGRES_URL`, на PostgreSQL. Каждый тест получает отдельную схему PostgreSQL. Локальная PostgreSQL в Docker:

```bash
docker run -d --rm --name office-pg-test -e POSTGRES_USER=office -e POSTGRES_PASSWORD=office -e POSTGRES_DB=office -p 127.0.0.1:55432:5432 postgres:17
```

```bash
(cd apps/office/api && OFFICE_TEST_POSTGRES_URL=postgresql://office:office@127.0.0.1:55432/office uv run pytest)
```

Тесты рабочей области используют локальный bare-репозиторий с раскладкой монорепозитория и не обращаются к сети. Тесты с реальным Docker помечены `docker` и запускаются отдельно. Они требуют собранный образ `back-office-sandbox:p4` и клонируют монорепозиторий из `OFFICE_TEST_TARGET_REPO` (по умолчанию `https://github.com/SlavaPush/vibe-studio.git`). Источник должен содержать ветку `main`: клон офиса берёт `origin/main`. Подходит путь к локальной копии `vibe-studio`, тогда проверяется `apps/chat` её ветки `main`. В CI job `office-sandbox` создаёт `main` на проверяемом commit (`git update-ref refs/heads/main HEAD`) и передаёт путь checkout:

```bash
(cd apps/office/api && OFFICE_TEST_DOCKER=1 OFFICE_TEST_TARGET_REPO="$PWD/../../.." uv run pytest -m docker)
```

Smoke-проверка локальной модели (ответ без рассуждения и с рассуждением, код возврата 0 только при двух завершённых ответах):

```bash
cd api && uv run python scripts/smoke_ollama.py qwen3:8b
```

Smoke-проверка шлюза ролей: по одному реальному вызову Anthropic, OpenAI и Ollama со схемой ответа QA (вызовы облачных провайдеров платные; код возврата 0 только при ответах по схеме от всех проверенных провайдеров). Аргументы ограничивают проверку названными провайдерами, например только локальной моделью:

```bash
cd api && PYTHONPATH=. uv run --env-file ../.env python scripts/smoke_roles.py
cd api && PYTHONPATH=. uv run --env-file ../.env python scripts/smoke_roles.py ollama
```

Образ sandbox и сквозная проверка: сборка `apps/chat/web` внутри контейнера и открытие собранного приложения в браузере Playwright. Каталог `apps/chat/web` монорепозитория монтируется только для чтения. Сборка интерфейса чата читает примеры из `../contracts/api.md`, поэтому `apps/chat/contracts` монтируется в `/work/contracts`. ## Ручной сценарий `P4`

Сценарий проверяет критерий этапа `P4` на реальных моделях в профиле `hybrid`: облачные вызовы платные (до 30 обращений на задачу). Экспорт диалога в Markdown в сценарии не ставится: это первая функция демонстрации.

1. Подготовка. Пересобрать образ sandbox (`docker build -t back-office-sandbox:p4 apps/office/docker/sandbox` из корня монорепозитория). В `.env` задать `TARGET_REPO_URL=git@github.com:SlavaPush/vibe-studio.git`, `OFFICE_CODES_DATABASE_URL` и выдать участникам личные коды с ролью офиса (раздел «Вход по личному коду»), новую SQLite в `OFFICE_DATABASE_URL`, ключи Anthropic и OpenAI. Запустить API на `127.0.0.1:8001` и панель на `http://localhost:5173` (раздел «Запуск локально»).
2. Участник А работает в панели, участник Б — через `curl` с отдельным файлом cookie. А ставит две задачи по интерфейсу `vibe-chat` и одну постороннюю, Б — две задачи. Ожидание: четыре задачи приняты, посторонняя отклонена с причиной; три задачи занимают слоты, четвёртая в `queued`; `GET /api/slots` показывает 3 из 3; в `workspace/wt/` три каталога на ветках `office/<task_id>`.
3. Дождаться события `decision_required` у трёх задач в слотах, ничего не утверждая. Остановить API и запустить снова. Ожидание: у трёх задач сохранились статус `awaiting_spec_approval`, требования и `version`, четвёртая осталась в `queued`. Затем А утверждает свои требования в панели, Б — через `curl`; после утверждения у каждой задачи появляется `role_started` разработчика.
4. Права. А открывает задачу Б: кнопки решений недоступны, видна причина. Б через `curl` пытается утвердить и отменить задачу А: ответ `403 forbidden_not_owner`. Для проверки выпуска в БД создаётся кандидат `pending` через `TaskStore.create_candidate`: А видит его без кнопок выпуска, Б через `curl` получает `403 forbidden_role`.
5. По событиям `role_started`, `tool_called` и `check_result` трёх задач построить интервалы работы и убедиться, что они пересекаются, пока четвёртая задача в `queued`.
6. Когда задача доходит до `awaiting_integration` или отменяется, четвёртая получает слот и worktree.
7. У задачи в `awaiting_integration` проверить отчёт проверок (`commit_sha`, `suite_hash`), артефакты `review-*-qa.json` и `review-*-critic.json` и два отчёта Playwright: тест QA не проходит на `base_sha` и проходит на commit задачи.
8. Записать длительность шагов по событиям, число обращений к моделям (`usage`), замечания QA и критика, события `tool_called` с `denied` и итоговые статусы задач.

Во время сценария наблюдать `docker stats` и `ollama ps`: два контейнера проверок по 3 GB и `qwen3:8b` занимают память одновременно. При нехватке памяти уменьшить `OFFICE_SANDBOX_CONTAINERS` до 1.
