# Интеграции офиса: GitHub, Render и `vibe-chat`

Документ описывает, как офис взаимодействует с внешними системами при работе над задачей и выпуске. Реализация этих механизмов — этапы `P4` и `P5`. На этапе `P1` документ фиксирует обязательные гарантии, на которые опираются контракт `contracts/api.md` и панель.

Внешние действия выполняет обычный код релизного адаптера, а не агент. Каждое действие записывается в журнал операций до вызова и сверяется с фактическим результатом после него. Неизвестный исход внешней операции не разрешает повторный вызов вслепую.

## Секреты и права

| Секрет | Где хранится | Кто использует | Права |
| --- | --- | --- | --- |
| Ключ GitHub App (`*.pem`) | Файл вне репозитория; путь — `GITHUB_APP_PRIVATE_KEY_PATH` в `.env` офиса, там же `GITHUB_APP_ID` и `GITHUB_APP_INSTALLATION_ID` | Релизный адаптер | Ключ GitHub App офиса (например, `vibe-office`), установленного только в репозиторий `SlavaPush/vibe-studio`. Релизный адаптер получает по ключу короткоживущий токен установки. Права App: Contents — read and write, Pull requests — read and write, Checks — read, Commit statuses — read, Actions — read, Metadata — read. Права Workflows, Administration, Checks — write и Commit statuses — write не выдаются. App и ключ создаёт владелец на этапе `P5` |
| Ключ Render API | `.env` офиса | Релизный адаптер | Доступ к сервису Render `elbrus-vibe-chat` (`srv-dbdtap5g1s2s73b13edg`), который публикует `vibe-chat` из `apps/chat` |

Sandbox, агенты и CI не получают эти секреты. Агент не может изменить workflow GitHub Actions, настройки деплоя и политику путей.

GitHub App офиса не входит в список обхода ruleset `main` (`.github/rulesets/main.json`, раздел «Ruleset `main`» корневого `README.md`). Обходит ruleset только роль администратора репозитория.

## GitHub

### Рабочая копия и ветка задачи

1. Офис держит клон монорепозитория `https://github.com/SlavaPush/vibe-studio.git` в `workspace/vibe-studio` (каталог в `.gitignore`). Целевое приложение — `apps/chat`.
2. Для новой задачи выполняются `git fetch origin` и `git worktree add --no-checkout workspace/wt/<task_id> -b office/<task_id> origin/main`, затем в worktree включается sparse checkout в режиме cone только для `apps/chat/` и выполняется checkout ветки. Каталогов `apps/office/` и `.github/` в worktree нет. SHA `origin/main` записывается в поле задачи `base_sha`.
3. Разработчик и QA меняют файлы только внутри `workspace/wt/<task_id>` и только в разрешённых путях `apps/chat/web/` (`apps/chat/web/src/**`, `apps/chat/web/public/**`, `apps/chat/web/index.html`; тесты QA — `apps/chat/web/e2e/office/**/*.pw.ts`). Пути политики заданы относительно корня монорепозитория.
4. Политику путей и собственный код офис читает только из своего checkout (`apps/office/policies/paths.yaml` каталога, из которого запущен офис), никогда из клона или worktree задачи. Изменение политики в ветке задачи не меняет решений офиса.
5. Перед переходом задачи в `awaiting_integration` офис повторно проверяет всю ветку `base_sha..HEAD`: каждый изменённый путь допустим для одной из ролей, режим файла обычный (`100644`), содержимое не двоичное, добавленные строки не содержат комментариев отключения проверок (`eslint-disable`, `oxlint-disable`, `@ts-ignore`, `@ts-nocheck`, `@ts-expect-error`). Нарушение переводит задачу в `needs_attention` с причиной, PR не создаётся. Та же проверка (`app/branch_check.py`) выполняется перед каждым push ветки задачи и релизным этапом перед выпуском.
6. Переход в `awaiting_integration` освобождает слот задачи, worktree сохраняется. Worktree удаляется только при закрытии задачи (`cancelled`, `released`). Ветка `office/<task_id>` остаётся до слияния или закрытия PR.
7. Ветка отправляется командой `git push <адрес> <head_sha>:refs/heads/office/<task_id>` из worktree задачи без `--force`. Адрес — `https://github.com/<OFFICE_GITHUB_REPO>.git`. Токен установки GitHub App передаётся git только через переменные окружения процесса push: `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=AUTHORIZATION: basic <base64("x-access-token:<токен>")>`; там же отключаются hooks (`core.hooksPath`), список credential helper сбрасывается пустым значением `credential.helper`, `core.askPass` очищается, а `GIT_ASKPASS`, `SSH_ASKPASS` и `GIT_CONFIG_PARAMETERS` не наследуются: при отказе GitHub в токене push не выполняется с учётными данными владельца. Токена нет в аргументах команды, в адресе, в `.git/config` клона, в журнале API и в тексте ошибок: вывод git push не сохраняется, результат классифицируется как успех, отказ GitHub (`rejected`) или неизвестный исход.
8. После успешного push SHA сохраняется в поле задачи `head_sha`, в журнал задачи пишется вызов инструмента `git_push`. Отказ GitHub (ветка изменена вне офиса, push запрещён) переводит задачу в `needs_attention`.

### Pull request

1. Офис отправляет ветку `office/<task_id>` в `vibe-studio` по HTTPS с токеном установки GitHub App (пункт 7 раздела «Рабочая копия и ветка задачи»). Push в `main`, force push и изменение защиты веток не выполняются.
2. Перед созданием PR офис ищет открытый PR ветки: `GET /repos/{repo}/pulls?head=<owner>:office/<task_id>&state=open`. Найденный PR сохраняется в задаче. Иначе PR создаётся запросом `POST /repos/{repo}/pulls` с `head = office/<task_id>`, `base = main`, заголовком — названием задачи и телом из цели, критериев приёмки, итогов QA и критика. Автор ветки и PR — GitHub App офиса. Номер и адрес PR сохраняются в полях задачи `pr_number` и `pr_url`, в журнал пишется событие `pr_opened`. Задача остаётся в `awaiting_integration`.
3. Отмена задачи в `awaiting_integration` (решение `cancel`) закрывает PR: `PATCH /repos/{repo}/pulls/{number}` с `state = closed`, событие `pr_closed`. Если ответ на создание PR был потерян, офис после отмены находит PR поиском по `head` и закрывает его.
4. Слияние PR выполняет офис после решения агента ревью (раздел «Решение агента ревью PR» и «Слияние»); выпуск — этап `P5.3`. Офис не разрешает конфликты автоматически и не обходит защиту веток.
5. Ruleset `main` действует на App так же, как на любого участника без права обхода:
   - контур интерфейса: PR, меняющий только файлы без владельца в `.github/CODEOWNERS`, сливается без одобрений (`required_approving_review_count: 0`);
   - серверный контур: PR, меняющий файлы с владельцем в `.github/CODEOWNERS`, сливается только после одобрения владельца `@SlavaPush`. Автор PR — App, а не владелец, поэтому владелец может одобрить PR. Новый push снимает прежнее одобрение. На этапе `P4a` такие PR офиса всё равно отклоняются политикой путей и проверкой `office-paths` независимо от одобрения; серверный контур включается на этапе `P5`;
   - обязательные проверки ruleset привязаны к GitHub Actions (`integration_id: 15368`). Статус или check run с тем же именем, созданный токеном App, не засчитывается. Права Checks — write и Commit statuses — write у App нет.
6. Без права Workflows токен установки App не может отправить ветку, в которой изменены файлы `.github/workflows/**`: GitHub отклоняет такой push до создания PR. Эта граница действует независимо от ruleset.
7. Итоговый commit слияния — `sha` ответа на запрос слияния или, при сверке, `merge_commit_sha` из `GET /repos/{repo}/pulls/{number}`. Он сохраняется в поле задачи `merge_sha`; дальнейшие проверки и выпуск относятся к этому commit.

### Обязательные проверки PR

1. Список обязательных проверок офис читает из `.github/rulesets/main.json` своего checkout (корень монорепозитория, из которого запущен офис), а не из ветки задачи. Workflow и событие каждой проверки берутся из `.github/workflows/*.yml` того же checkout: job `ci.yml` проверяются запусками события `pull_request`, job `office-paths` из `office-paths.yml` — запуском события `pull_request_target`.
2. Перед подсчётом офис читает PR (`GET /repos/{repo}/pulls/{number}`). PR закрыт вне офиса — задача переходит в `needs_attention`. `head.sha` PR не равен `head_sha` задачи и ветка `office/<task_id>` указывает на другой commit — ветку изменили вне офиса, проверки не засчитываются, задача переходит в `needs_attention`, PR не закрывается. Если ветка указывает на `head_sha`, а PR ещё не обновился, офис ждёт. Затем офис читает запуски `GET /repos/{repo}/actions/runs?head_sha=<head_sha>`. Для проверки засчитывается последний по `run_number`, затем `run_attempt` запуск нужного workflow (`path`) с нужным событием (`event`), `head_sha`, равным текущему head задачи, и номером PR задачи в `pull_requests`. Запуск другого PR, другого head, без номера PR или устаревшая попытка не засчитываются.
3. Происхождение запуска проверяется по check suite: `GET /repos/{repo}/check-suites/{check_suite_id}` должен вернуть `app.id = 15368` (GitHub Actions). Итог проверки — `status` и `conclusion` job с именем проверки из `GET /repos/{repo}/actions/runs/{run_id}/jobs`.
4. Каждое изменение сводки сохраняется в поле задачи `checks` и публикуется событием `checks_status`. Только `conclusion = success` засчитывается. Все проверки `success` — задача остаётся в `awaiting_integration`, офис вызывает агента ревью PR.
5. Любой другой итог завершённой обязательной проверки (`failure`, `cancelled`, `timed_out`, `action_required`, `skipped`, `neutral`, `stale`) закрывает PR и переводит задачу в `failed` с `failure_kind = checks_failed` и перечнем проверок. Повтор такой задачи запрещён.
6. Если хотя бы одна обязательная проверка не завершилась (засчитанного запуска нет или job выполняется), PR или проверки не читаются (ошибка GitHub, сеть) или head PR не обновился дольше `OFFICE_CHECKS_TIMEOUT_MINUTES` (по умолчанию 30) с последнего push или открытия PR, задача переходит в `needs_attention`. PR остаётся открытым.

### Проверка путей `office-paths`

1. Workflow `.github/workflows/office-paths.yml` запускается событием `pull_request_target` (`opened`, `synchronize`, `reopened`). Job `office-paths` выполняется только для веток `office/*`.
2. Checkout берёт базовую ветку без `ref` и с `persist-credentials: false`: код проверки и политика путей — доверенные. Объекты head PR получаются `git fetch` только как данные. Код из head не выполняется: ни скрипты, ни зависимости, ни конфигурации.
3. Проверка — скрипт офиса `apps/office/api/scripts/check_branch.py` из базовой ревизии (`uv run python -m scripts.check_branch`). Он использует ту же функцию, что повторная проверка ветки, и считает diff от merge-base базового commit и head PR.
4. У workflow `permissions: contents: read`, секретов нет. SHA базового commit и head PR передаются через `env`, а не подстановкой в текст скрипта.
5. На этапе `P4a` любые пути вне зоны интерфейса отклоняются. Серверный контур с одобрением владельца добавляется на этапе `P5`.

### Решение агента ревью PR

1. Агент ревью PR (роль `pr_reviewer`, маршрут — `policies/models.yaml`; в профилях `cloud` и `hybrid` — сильная облачная модель с резервной) вызывается только для head PR, у которого все обязательные проверки PR `success` и повторная проверка ветки `verify_branch` (`app/branch_check.py`) не нашла нарушений. Нарушение ветки — `needs_attention`, агент не вызывается. Агент не получает инструментов и токенов; вызов выполняет поток исполнителя выпуска вне транзакций.
2. Вход собирается как данные, а не инструкции: текст задачи, требования и критерии приёмки, сводка обязательных проверок PR для этого head, итоги QA и критика последнего цикла, изменённые файлы, чек-лист (изменённые пути, новые сетевые вызовы, навигация на внешние URL, новые поля ввода, скрытие системных сообщений, изменение отправляемого текста, скопированный сторонний код) и diff `base_sha..head_sha` с пометкой об обрезке.
3. Ответ проверяет код: `verdict` (`approve` или `reject`), непустое `reasons`, `checklist` — ровно по одному пункту чек-листа с `ok` и `note`, `required_changes` — не пуст при `reject`; `approve` допустим только при `ok` во всех пунктах. Невалидный или неполный ответ, таймаут, ошибка основного и резервного провайдеров, вход больше окна модели, исчерпанный предел обращений — решение не принимается, задача переходит в `needs_attention`, PR остаётся открытым (fail-closed).
4. Решение сохраняется в таблице `pr_reviews` (`task_id`, `head_sha`, `verdict`, `reasons`, `required_changes`, `checklist`, `model`, `created_at`) вместе с завершением операции `pr_review:<task_id>:<head_sha>` и событием `pr_review` одной транзакцией. Решение действительно только для своего `head_sha`. Повторная обработка того же head использует сохранённое решение и не обращается к модели.
5. Предел обращений агента ревью на задачу — `OFFICE_PR_REVIEW_CALLS` (по умолчанию 2), отдельно от бюджета графа (`model_calls_limit`): исчерпанный бюджет разработки не блокирует ревью. Переход на резервную модель выполняется внутри одного обращения.
6. Операция `pr_review`, оставшаяся в `started` после перезапуска (ответ мог быть получен, но не сохранён), получает `unknown`, задача — `needs_attention`; автоматического повторного обращения нет. Новое обращение выполняется только после решения `retry` владельца задачи или администратора и только в пределах `OFFICE_PR_REVIEW_CALLS`.
7. `reject` закрывает PR (операция `close_pr`), задача получает `failed` с `failure_kind = pr_rejected`; обоснование и что изменить видны в поле задачи `pr_review` и в причине остановки. Повтор такой задачи запрещён. Решение агента не отменяет детерминированных проверок: `approve` не открывает слияние при непрошедшей проверке.

### Слияние

1. После `approve` офис перечитывает PR (`GET /repos/{repo}/pulls/{number}`). PR закрыт — `needs_attention`. Head PR не равен `head_sha` решения — решение недействительно (остаётся в истории), слияние не выполняется, задача `needs_attention`: после открытия PR офис ветку не меняет, поэтому новый head — изменение извне. Автоматического нового цикла ревью нет.
2. Слияние — операция `merge_pr:<task_id>:<head_sha>`. Проверка статуса задачи, запись операции и событие `merge_started` выполняются одной транзакцией с той же блокировкой, что решения по задаче, поэтому `cancel` либо принят до операции (слияния нет), либо отклоняется. Запрос: `PUT /repos/{repo}/pulls/{number}/merge` токеном установки App с телом `{"sha": "<head_sha решения>", "merge_method": "squash", "commit_title": "<название задачи> (#<номер PR>)"}`. Параметр `sha` не даёт GitHub слить другой head. Ruleset `main` действует на App без обхода.
3. Ответ `200` с `merged = true` — `sha` ответа сохраняется в `merge_sha` задачи, событие `pr_merged`; результат операции, `merge_sha` и событие фиксируются одной транзакцией.
4. Ответ `4xx` (`405`, `409`, `422`) — офис перечитывает PR: PR слит с head решения — результат принимается как успех; head изменился — решение недействительно; иначе операция `failed`, задача `needs_attention` с кодом ответа. Новый запрос слияния — только после `retry` владельца задачи или администратора.
5. Таймаут, разрыв соединения или ответ `5xx` оставляют операцию `started`. Дальше выполняется только сверка, повторного `PUT` нет никогда: `GET /pulls/{number}` — `merged = true` с `merge_commit_sha` и прежним head — `succeeded`; PR открыт — операция остаётся `started`, сверка повторяется; PR закрыт без слияния или слит с другим head — `unknown`. Исход не установлен за `OFFICE_RECONCILE_TIMEOUT_MINUTES` — `unknown`, задача `needs_attention`; `retry` возобновляет только сверку.
6. После подтверждённого слияния (`merge_sha` заполнен) и при операции `merge_pr` в статусе `started` или `unknown` решение `cancel` отклоняется. Если отмена записана одновременно со слиянием, исполнитель завершает сверку, сохраняет `merge_sha` и не закрывает слитый PR.

### Обязательные проверки итогового commit

1. После слияния офис читает запуски `GET /repos/{repo}/actions/runs?head_sha=<merge_sha>`. Обязательные проверки итогового commit — job из списка ruleset `main`, у workflow которых есть событие `push` (job `ci.yml`; `office-paths` на `push` не запускается). Засчитывается последний запуск workflow с событием `push`, `head_sha = merge_sha` и веткой `main`; происхождение — check suite GitHub Actions (`app.id = 15368`), итог — job с именем проверки. Сводка сохраняется в поле задачи `checks` (`head_sha = merge_sha`), событие `checks_status`.
2. Только `conclusion = success` засчитывается. Любой другой итог завершённой проверки — задача `failed` с `failure_kind = checks_failed`, кандидат выпуска не создаётся. При `conclusion = failure` хотя бы одной проверки изменение уже в `main` и сломало его: в той же транзакции создаётся кандидат `kind = release` со статусом `failed` (`commit_sha = merge_sha`, `expected_previous_sha` — родитель первой линии, `ci_run_ids`, `blocked_reason` — причина), и выпуск блокируется через набор отмены (раздел «Revert-PR»): revert-PR тем же механизмом, без Render rollback (деплоя не было). Другие итоги (`cancelled`, `skipped` и подобные) revert не запускают. Проверки не завершились или не прочитаны за `OFFICE_CHECKS_TIMEOUT_MINUTES` после слияния — `needs_attention`, revert нет.
3. Результаты проверок PR не заменяют проверки итогового commit.
4. Идентификаторы засчитанных запусков сохраняются в поле кандидата `ci_run_ids`.

### Критический E2E итогового commit

1. После успешных проверок итогового commit офис получает `main` в свой клон (`git fetch origin main`) и выполняет набор sandbox на временном checkout `merge_sha`: `lint`, `test`, `build` и `e2e` со всеми тестами QA из `apps/chat/web/e2e/office/` этого commit (`Sandbox.run_suite(..., require_e2e=True)`). Отчёт сохраняется в `check_reports` с `commit_sha = merge_sha` и `suite_hash`.
2. Ненулевой код любого шага набора — задача `failed` с `failure_kind = checks_failed`, кандидат выпуска не создаётся; как в пункте 2 предыдущего раздела, создаётся кандидат `failed` с отчётом `e2e` и выпуск блокируется до публикации revert. Для commit исправления (revert-PR) непрошедший набор — `revert.status = needs_attention`. Ошибка sandbox или неполный набор (например, не установились зависимости) — `needs_attention`.
3. Повторная обработка использует только полный сохранённый отчёт для `merge_sha` (все четыре шага и `suite_hash`); неполный отчёт — набор выполняется заново.

### Кандидат выпуска

1. Основание выпуска `expected_previous_sha` — опубликованная сейчас версия после согласования публикации (раздел «Согласование публикации»). Пока в очереди есть активный выпуск или операция деплоя или отката не завершена, кандидат не создаётся: задача остаётся в `awaiting_integration` до следующего прохода. Недоступная версия сервиса, неоднозначный или посторонний commit — `needs_attention`, кандидат не создаётся.
2. Кандидат `kind = release` (`commit_sha = merge_sha`, `expected_previous_sha`, `spec_hash`, `suite_hash` и отчёт `e2e` критического E2E, `ci_run_ids`, `pr_url`, `pr_review_id` решения агента, `origin = task`) и переход задачи в `awaiting_release` фиксируются одной транзакцией. Для одной задачи и одного `merge_sha` существует не больше одного действующего обычного кандидата (частичный уникальный индекс по `task_id`, `commit_sha` с условием `kind = 'release' AND status <> 'revoked'`); отозванный кандидат заменяется новым кандидатом того же commit. Кандидаты отката этим индексом не ограничиваются.

## Журнал операций

Внешние операции, изменяющие состояние GitHub (push ветки задачи, создание, слияние и закрытие PR) и Render (деплой, откат), и обращение к агенту ревью PR выполняет один поток исполнителя выпуска. За проход он обрабатывает задачи в `awaiting_integration` (в том числе после слияния до создания кандидата) и отменённые задачи с открытым или, возможно, созданным PR (есть `pr_number` без успешного закрытия и без `merge_sha` либо операция `create_pr`, `close_pr` или `merge_pr` в статусе `started` или `unknown`), затем revert-PR заблокированного выпуска, затем очередь выпуска. Для отменённой задачи операции push не сверяются и не мешают закрыть PR. Поток запускается после восстановления worktree при старте API, просыпается по сигналу смены статуса задачи, решения по задаче или выпуску и раз в `OFFICE_RELEASE_POLL_SECONDS` секунд (по умолчанию 20). Без настроек GitHub App поток не запускается; в журнал API пишется одно предупреждение.

1. Каждая операция записывается в таблицу `operations` отдельной транзакцией до вызова: `kind` (`push`, `create_pr`, `pr_review`, `merge_pr`, `close_pr`, `revert`, `deploy`, `rollback`), уникальный `key` (`push:<task_id>:<sha>`, `create_pr:<task_id>`, `pr_review:<task_id>:<head_sha>`, `merge_pr:<task_id>:<head_sha>`, `close_pr:<task_id>`; для revert-PR вместо `<task_id>` — `revert:<release_id>` (попытка `n > 1` — `revert:<release_id>:<n>`), например `create_pr:revert:<release_id>`; `revert:<release_id>` (`revert:<release_id>:<n>`), `deploy:<release_id>`, `rollback:<release_id>`), `status = started`, номер попытки `attempt`; операции revert-PR и очереди хранят `release_id`. Результат (`succeeded` с `external_ref`, `failed` или `unknown` с `detail`) записывается после вызова. Внешний вызов не выполняется внутри транзакции с блокировкой.
2. Результат успешного вызова, поля задачи (`head_sha`, `pr_number`, `pr_url`, `merge_sha`) или решение агента ревью и событие фиксируются одной транзакцией. Если эта транзакция не выполнена, операция остаётся `started` и сверяется на следующем проходе.
3. За один шаг выполняется не больше одного изменяющего вызова. Перед изменяющим вызовом статус задачи перечитывается из БД.
4. Повторный вызов разрешён только для операции в статусе `failed` (отсутствие результата доказано ответом GitHub или сверкой); попытка увеличивает `attempt`. Операция `succeeded` не повторяется. Операция `started` или `unknown` сначала сверяется.
5. Сверка по типам:
   - `push`: `GET /repos/{repo}/git/ref/heads/office/<task_id>`. SHA ветки равен SHA операции — `succeeded`. Ветки нет или её SHA — предок SHA операции — `failed` с пометкой `retry: idempotent`: повтор push того же commit без `--force` не меняет ветку или только продвигает её к тому же commit. Это единственное исключение из правила «повтор только при доказанном отсутствии результата». Иначе ветку изменили вне офиса — `unknown`;
   - `create_pr`: поиск открытого PR ветки. Найден — `succeeded` с номером. Не найден и закрытых PR ветки нет — `failed`. Найден только закрытый PR — `unknown`;
   - `close_pr`: `GET /repos/{repo}/pulls/{number}`. `state = closed` — `succeeded`, `open` — `failed`;
   - `merge_pr`: `GET /repos/{repo}/pulls/{number}`. `merged = true` с head решения — `succeeded` с `merge_commit_sha`; PR открыт — исход не установлен, операция остаётся `started`; закрыт без слияния или слит с другим head — `unknown`. Повторного запроса слияния после таймаута нет;
   - `pr_review`: решение для head сохранено — `succeeded`; после `retry` владельца задачи или администратора, записанного позже начала операции, — `failed` (разрешено новое обращение в пределе); иначе `unknown` и `needs_attention`.
6. Таймаут или разрыв соединения во время вызова оставляет операцию `started`; повторный вызов вслепую не выполняется. Ошибка сети во время сверки оставляет операцию `started` до следующего прохода. Ответ GitHub `4xx` на создание PR записывает `failed` и переводит задачу в `needs_attention`; на закрытие PR — `unknown`. После трёх попыток без установленного исхода операция получает `unknown`.
7. Операция, исход которой не установлен за `OFFICE_RECONCILE_TIMEOUT_MINUTES` (по умолчанию 30) с начала попытки или с последней смены статуса задачи (`retry`, `cancel`), получает `unknown` без изменяющего вызова. Задача в `awaiting_integration` переходит в `needs_attention` с причиной. Для отменённой задачи статус не меняется: пишется событие `operation_unknown` с типом операции и номером PR, исполнитель больше не обрабатывает эту задачу. Неизвестный исход push отменённой задачи (в том числе отменённой во время сверки) события не создаёт и закрытию PR не мешает. Операция `unknown` создания или закрытия PR, записанная до отмены, сверяется после `cancel` заново.
8. `retry` задачи в `needs_attention`, у которой есть операции выпуска или заполнены `head_sha` или `pr_number`, возвращает её в `awaiting_integration`. Такой `retry` может записать владелец задачи или администратор. Исполнитель сначала сверяет операции `started` и `unknown`; если исход по-прежнему не установлен, задача снова получает `needs_attention`.
9. В `operations.detail`, событиях, журнале API и тексте ошибок нет токена установки, JWT и заголовков запросов. Ошибка клиента GitHub содержит только метод, путь без параметров запроса и код ответа.

## Очередь выпуска

1. Одновременно выполняется не больше одного выпуска `vibe-chat`: активный кандидат хранится в `scheduler.active_release_id`. Захват и освобождение очереди выполняются в транзакции с блокировкой строки `scheduler`; внешние вызовы — вне транзакции.
2. Кандидат появляется в статусе `pending`, задача — в `awaiting_release`. Подтверждения администратора нет: кандидат деплоится, как только очередь свободна. Без `RENDER_API_KEY` и `RENDER_SERVICE_ID` очередь не запускается: кандидаты ждут в `pending`, `GET /api/release-queue` возвращает `configured = false`, панель показывает «Выпуск не настроен».
3. Порядок выбора, когда очередь свободна и нет незавершённых операций `deploy` и `rollback`:
   - кандидаты отката (`kind = rollback`) деплоятся первыми, в порядке создания;
   - из обычных кандидатов выбирается самый новый по истории `main`: кандидат A — предок B, если `GET /repos/{repo}/compare/{A}...{B}` возвращает `status = ahead` и `behind_by = 0`. Ожидающие кандидаты — предки выбранного — получают `superseded` (`superseded_by` — выбранный) в транзакции захвата; их задачи получают `released` с пометкой «Опубликовано в составе <commit>» после публикации выбранного. Если деплой выбранного завершился ошибкой без отката, предки возвращаются в `pending`; если выбранный откатан, их задачи получают `failed` (`verify_failed`): revert отменяет все слияния PR офиса из диапазона выпуска;
   - кандидаты с заполненным `blocked_reason` (остановлены) не выбираются до решения `resume_releases`.
4. Перед деплоем выполняются согласование публикации, сверка основания, проверка деплоев вне офиса и проверка состава (разделы ниже), затем захват очереди и операция `deploy:<release_id>` (для отката — `rollback:<release_id>`). Кандидат получает `deploying`, задача — `deploying`.
5. После блокировки (`release_blocked_by`, раздел «Откат») деплоятся только кандидаты отката и обычные кандидаты, чей `commit_sha` совпадает с исправляющим commit (`revert.fix_sha` откатанного кандидата) или является его потомком.

### Согласование публикации

Офис читает `GET <OFFICE_SERVICE_URL>/api/version` (по умолчанию `https://elbrus-vibe-chat.onrender.com`, поле `version` — первые 7 символов SHA, без кеширования) перед созданием кандидата, перед деплоем и в `resume_releases`:

1. Версия — префикс `commit_sha` кандидата офиса в статусе `released`: этот кандидат получает `is_published = true`, остальные — `false`.
2. Иначе публикация выполнена вне офиса: версия разрешается в полный SHA (`GET /repos/{repo}/commits/{version}`), commit должен входить в историю `main` (`GET /repos/{repo}/compare/{sha}...main`: `status` `ahead` или `identical`, `behind_by = 0`). У всех кандидатов `is_published = false`, `scheduler.published_sha` = полный SHA, в задачи ожидающих кандидатов пишется событие `external_publish`. `published_sha` служит основанием, пока офис не опубликует своего кандидата.
3. Ожидающие обычные кандидаты, чей `commit_sha` совпадает с опубликованным или является его предком, получают `superseded`; их задачи — `released` с пометкой «Опубликовано в составе <commit>» (при внешней публикации — «(внешний деплой)»). Публикация предка опубликованного commit исключена.
4. Пока очередь занята (активный кандидат или операция `deploy`, `rollback` в статусе `started` или `unknown`), версия только читается: `is_published`, `published_sha` и итоги задач не меняются, новый кандидат не создаётся. Публикацию своего кандидата фиксирует только успешная проверка после деплоя.
5. Перед созданием кандидата и перед деплоем чтение версии повторяется раз в 5 секунд в пределах `OFFICE_VERIFY_SECONDS` (по умолчанию 120): спящий сервис Render Free просыпается дольше одного запроса. Таймаут одного запроса — 60 секунд, но не больше остатка окна (не меньше 1 секунды). При остановке офиса ожидание прерывается без изменения состояния.
6. Версия недоступна после исчерпания окна, не содержит SHA или commit не из `main` — деплой не начинается: кандидат получает `blocked_reason`, задача — `needs_attention`, очередь свободна.

### Сверка основания

Непосредственно перед деплоем `expected_previous_sha` кандидата сравнивается с согласованной опубликованной версией. Расхождение — кандидат получает `revoked` с причиной в `blocked_reason`, и офис создаёт нового кандидата того же `commit_sha` с новым основанием; `task_id`, `origin`, проверки и E2E переносятся (они относятся к `commit_sha`), состав выпуска проверяется заново относительно нового основания. Кандидат отката при расхождении получает `revoked` без замены.

### Состав выпуска

Перед деплоем обычного кандидата каждый commit первой линии `main` в диапазоне `expected_previous_sha..commit_sha` (`GET /repos/{repo}/compare/{base}...{head}`, первый родитель каждого commit) должен иметь положительно подтверждённое происхождение:

1. Слитый PR (`GET /repos/{repo}/commits/{sha}/pulls`: `merged_at` заполнен, `merge_commit_sha = sha`; автор слияния — `merged_by.login` из `GET /repos/{repo}/pulls/{number}`):
   - PR офиса: `merged_by.login = <OFFICE_GITHUB_APP_SLUG>[bot]` (по умолчанию `vibe-office[bot]`), в журнале есть успешная операция `merge_pr` с `external_ref = sha`, успешный push того же head (push выполняется только после `verify_branch`), решение агента ревью `approve` для head и сводка `checks_status` для head, где все проверки `success`;
   - PR, слитый человеком: `merged_by.login` входит в `OFFICE_TRUSTED_GITHUB_LOGINS` (по умолчанию `SlavaPush`).
2. Прямой push: `GET /repos/{repo}/activity?ref=refs/heads/main&activity_type=push` (до 10 страниц по 100 событий, переход по заголовку `Link`) содержит событие доверенного `actor.login` с `after = sha` или push нескольких commit, диапазон `before..after` которого содержит `sha`.
3. Иначе — проблема с SHA commit. Хотя бы одна проблема: деплоя нет, кандидат остаётся `pending` с `blocked_reason` («Состав выпуска не подтверждён: …»), задача — `needs_attention`, очередь свободна. Смешанный состав допустим: каждый commit подтверждается по своему правилу. Недоступный API GitHub — проверка повторяется на следующем проходе (fail-closed: без подтверждения деплоя нет).

### Деплои вне офиса

1. Перед деплоем: в `GET /v1/services/{serviceId}/deploys` есть нетерминальный деплой, которого нет в кандидатах офиса, — деплой не начинается, кандидат ждёт; время ожидания хранится в `scheduler.external_wait_since`. Дольше `OFFICE_EXTERNAL_DEPLOY_WAIT_MINUTES` (по умолчанию 30) — `blocked_reason`, задача `needs_attention`, очередь свободна.
2. Во время опроса деплоя и проверки после деплоя: появился более новый деплой (по `createdAt`), чем свой, или свой деплой стал `deactivated` — проверка прекращается, отката нет, кандидат получает `blocked_reason`, задача — `needs_attention`, очередь занята.
3. Непосредственно перед автоматическим откатом: офис читает `/api/version`, затем заново получает список деплоев Render; последний деплой — свой, `/api/version` равен своему `commit_sha` или недоступен. Иначе отката нет, `needs_attention`, очередь занята.
4. После проверки отката: офис заново получает статус деплоя отката и список деплоев. Деплой отката не `live` или появился более новый деплой — откат не признаётся успешным, блокировки и revert-PR нет, кандидат получает `blocked_reason`, задача — `needs_attention`, очередь занята.

## Render

1. Автодеплой сервиса Render `elbrus-vibe-chat` (`srv-dbdtap5g1s2s73b13edg`) выключен: в настройках Render Auto-Deploy = Off, через API — поле `autoDeploy = no` запроса Update service. Деплой из офиса выполняет только очередь; деплои других сессий владельца учитываются согласованием публикации и проверкой деплоев вне офиса.
2. Деплой — операция `deploy:<release_id>`, записанная в транзакции захвата очереди, затем `POST /v1/services/{serviceId}/deploys` с телом `{"commitId": "<commit_sha>"}` и ключом `Authorization: Bearer <RENDER_API_KEY>`. Ответ сохраняется в `deploy` кандидата (`render_deploy_id`, `render_status`) вместе с завершением операции и событием `deploy_status`. Ключ Render не попадает в исключения, журнал, события и `operations.detail`.
3. Офис опрашивает `GET /v1/services/{serviceId}/deploys/{deployId}` и список деплоев до терминального статуса. Каждое изменение статуса — событие `deploy_status`. Ожидание: `created`, `queued`, `build_in_progress`, `update_in_progress`, `pre_deploy_in_progress`.
4. `live` — кандидат переходит в `verifying` (раздел «Проверка после деплоя»).
5. `build_failed`, `update_failed`, `pre_deploy_failed`, `canceled` — ошибка деплоя: офис проверяет, что `/api/version` равен прежней версии (`expected_previous_sha`); кандидат `failed` с `deploy.error`, задача `failed` (`deploy_failed`), очередь освобождается, отката нет. Версия не прежняя или недоступна — `needs_attention`, очередь занята. `deactivated` своего деплоя — деплой вне офиса (раздел «Деплои вне офиса»).
6. Ответ `4xx` на `POST` — деплой не создан: операция `failed`, кандидат `failed`, задача `failed` (`deploy_failed`), очередь освобождается. Ответ `5xx` — исход не установлен.

### Неизвестный исход

Повторного `POST` деплоя или отката нет никогда. Операция `deploy` или `rollback` в статусе `started` сверяется по `GET /v1/services/{serviceId}/deploys`: деплой с `commit.id` цели, `createdAt` не раньше начала операции (с допуском 1 минута) и `trigger` (`rollback` для отката, иное — для деплоя).

| Момент остановки | Результат сверки |
| --- | --- |
| До запроса или после запроса без сохранённого ответа (неразличимы) | Ровно один подходящий деплой — его id сохраняется, опрос продолжается; не найден или найдено несколько — операция `unknown`, кандидат `blocked_reason`, задача `needs_attention`, очередь занята |
| После сохранения id | Опрос `GET .../deploys/{deployId}`, запроса нет |
| Во время проверки после деплоя или отката | Проверка начинается заново с начала окна |
| После терминального результата до записи переходов | Переходы применяются один раз: проверка повторяется, публикация фиксируется одной транзакцией |
| После успешного отката до создания revert-PR | Revert-PR создаётся один раз (операции `revert:<release_id>`, `create_pr:revert:<release_id>`) |
| На любом шаге повтора revert-PR (решение `resume_releases` без `fix_sha`) | Повторное решение с тем же `idempotency_key` возвращает прежний ответ; открытый PR прежней попытки закрывается один раз (`close_pr:revert:<release_id>:<n>:<номер PR>`; `started` после перезапуска завершается по состоянию PR), ветка создаётся заново операцией `revert:<release_id>:<n>`, новый PR — один (`create_pr:revert:<release_id>:<n>`) |
| Render недоступен при сверке | Операция остаётся `started`; через `OFFICE_RECONCILE_TIMEOUT_MINUTES` — `unknown` |

Продолжение после `unknown` — только решение администратора `resume_releases` (раздел «Возобновление»).

## Проверка после деплоя

1. После `live` офис проверяет сервис: `GET /healthz` → `{"status": "ok"}`, `GET /api/version` — префикс `commit_sha`, главная страница — `200` с `<meta name="app-version" content="<7 символов>">`, префикс `commit_sha`. Попытки повторяются раз в 5 секунд в пределах `OFFICE_VERIFY_SECONDS` (по умолчанию 120). Таймаут каждого запроса — 60 секунд, но не больше остатка окна (не меньше 1 секунды); пауза между попытками не выходит за окно. Поэтому проверка превышает окно не больше чем на 1 секунду на каждый из трёх запросов последней попытки. Результат — `verify` кандидата и событие `deploy_status` с `verified`.
2. Успех — кандидат `released`, `is_published = true`, прежний опубликованный — `false`, `scheduler.published_sha` очищается, задача `released`, очередь освобождается.
3. Неуспех обычного выпуска — автоматический откат (раздел «Откат»). Неуспех ручного отката — `needs_attention`, очередь занята.
4. Управляемый сбой `OFFICE_VERIFY_FAULT=1` (только для ручной проверки отката на реальном сервисе): проверка выпуска задачи (`kind = release`, `origin = task`) считается неуспешной без обращения к сервису, в `verify` и событии `deploy_status` — `fault = true`. Проверка кандидатов исправления (`origin = auto_revert` и `resume`), автоматического и ручного отката выполняется всегда реально.

## Откат

1. Автоматический откат выполняется один раз на кандидата: операция `rollback:<release_id>`, `POST /v1/services/{serviceId}/rollback` с телом `{"deployId": "<id>"}` (Render Roll back deploy: прежняя сборка без пересборки). `deployId` — `deploy.render_deploy_id` кандидата прежней версии, для версии без кандидата — последний деплой из списка с `commit.id = expected_previous_sha` и статусом `live` или `deactivated`. Не найден — `needs_attention`, очередь занята. Кандидат получает `rolling_back`, результат — в `rollback`, события `rollback_status`.
2. После `live` отката — реальная проверка с ожидаемой версией `expected_previous_sha`. Успех — кандидат `failed` с диагностикой (`verify`, `rollback`, `blocked_reason`), задача `failed` (`verify_failed`), прежний опубликованный кандидат остаётся `is_published`, очередь освобождается, выпуск блокируется: `scheduler.release_blocked_by` = кандидат, событие `release_blocked`.
3. Ошибка отката (`4xx` на запрос, неуспешный статус Render, неуспешная проверка после отката) или неизвестный исход — `needs_attention`, очередь занята.
4. Ручной откат — решение администратора `rollback` для опубликованного выпуска: кандидат `kind = rollback` (`commit_sha` — `expected_previous_sha` выбранного выпуска, `expected_previous_sha` — `commit_sha` выбранного, `origin = manual_rollback`) ждёт свободной очереди с приоритетом. Перед деплоем опубликованная версия должна быть `commit_sha` выбранного выпуска, иначе `revoked`. Деплой — Render rollback к деплою цели, затем реальная проверка. Успех — кандидат отката `released` и `is_published`, выбранный выпуск `rolled_back` (его `reason` — причина из решения), выпуск блокируется (`release_blocked_by` = выбранный выпуск или его слияния добавляются в набор отмены установленной блокировки), revert-PR. Задача выбранного выпуска и задачи выпусков в его составе (`superseded_by`) из `released` переходят в `failed` с `failure_kind = rolled_back` и причиной «Ручной откат администратора: <reason или «причина не указана»>» (событие `role_finished` с `step = release`, затем `status_changed`); остальные задачи слияний офиса из диапазона получают тот же итог при создании revert.
5. Блокировка одна на очередь. Автоматический и ручной откат и непрошедшие проверки итогового commit (раздел «Обязательные проверки итогового commit») проходят через одну функцию: при пустой блокировке кандидат становится её владельцем (`revert.targets` — он сам), при установленной — цель добавляется в `revert.targets` владельца, блокировка не заменяется (событие `release_blocked` с `blocked_by`).

## Revert-PR

1. После успешного автоматического или ручного отката или непрошедших проверок итогового commit офис возвращает `main` в исправное состояние через PR от App, а не прямым push. Носитель — задача владельца блокировки: события пишутся в неё с полем `revert_of`. Состояние — поле `revert` владельца, набор отмены — `revert.targets`.
2. Операция `revert:<release_id>`: worktree `workspace/wt/revert-<release_id>` на ветке `office/revert-<release_id>` от `origin/main`, `git revert --no-edit` от новых слияний к старым (порядок первой линии `origin/main`) каждого commit первой линии диапазонов `base_sha..head_sha` целей набора без `fixed_by`, который является слиянием PR офиса и ещё не отменён прежней попыткой (подтверждение — как для PR офиса в разделе «Состав выпуска»: успешная операция `merge_pr` с `external_ref` = SHA, push того же head, `approve` агента ревью и успешные проверки head). Commit владельца (прямой push, PR, слитый человеком) не отменяются. Слияний офиса в диапазоне нет — revert не создаётся, `revert.status = needs_attention` с причиной: исправление вносит владелец (`resume_releases` с `fix_sha`). Revert слияния офиса удаляет и тест QA задачи (`apps/chat/web/e2e/office/<task_id>.pw.ts`); политика путей это допускает. Конфликт — `revert.status = needs_attention`, блокировка сохраняется. До создания ветки задачи найденных слияний (операция `merge_pr` без `release_id`) получают `failed` с `failure_kind` источника цели и её причиной; задача, уже завершившаяся ошибкой другого вида (например, `deploy_failed`, а её изменение вошло в откатанный выпуск), получает новый `failure_kind` и причину (прежний итог — в событиях). Цели получают `merges` и `attempt` и при неудаче (нет слияний офиса, конфликт). После слияния revert-PR цели этой попытки получают `fixed_by` — итоговый commit.
3. Дальше — обычный конвейер тех же операций журнала с ключами `revert:<release_id>` (`revert:<release_id>:<n>` для попытки `n > 1`): `verify_branch`, push токеном App, PR (заголовок «Revert: <название задачи>», тело — откатанный выпуск и причина отката), обязательные проверки PR с `office-paths`, агент ревью PR (вход — diff revert, откатанный выпуск, причина отката; предел обращений задачи не расходуется, одно обращение на head), squash-слияние, проверки итогового commit и критический E2E (без шага `e2e`, если тестов QA в commit не осталось). Итог — кандидат исправления `origin = auto_revert` с `task_id` откатанного кандидата, `revert.status = merged`.
4. Непрошедшая проверка, отказ агента, ошибка или неизвестный исход операции — `revert.status = needs_attention` с причиной в `revert.reason`, PR при отказе или непрошедшей проверке закрывается. Администратор повторяет revert-PR решением `resume_releases` без `fix_sha` (раздел «Возобновление») или владелец исправляет `main` и вызывает `resume_releases` с `fix_sha`.
5. Пока заблокировано, очередь выбирает только кандидатов, содержащих принятые исправления всех целей: `revert.status = merged` (кандидат исправления создан после проверок итогового commit и критического E2E), у каждой цели есть `fixed_by`, и `commit_sha` кандидата равен или является потомком каждого `fixed_by` (для `source = resume` — `fix_sha`). `fix_sha`, который не прошёл проверку (`revert.status = needs_attention`) или ещё проверяется, выпуск не открывает. Публикация такого кандидата снимает блокировку (событие `release_unblocked`); состав проверяется до транзакции публикации (`GET /repos/{repo}/compare`). Публикация выпуска, начатого до сбоя, блокировку не снимает. Ожидающие кандидаты, не содержащие исправления, становятся предками опубликованного и получают `superseded`.
6. Цель добавлена при установленной блокировке (у цели нет `attempt` текущей попытки) и у владельца нет операций в `started` или `unknown`: исполнитель начинает новую попытку (`attempt + 1`, `source = auto`) со всеми целями без `fixed_by` — один PR, открытый PR прежней попытки закрывается. Цели слитого revert-PR уже имеют `fixed_by`, поэтому после слияния (пока проверяется итоговый commit, после создания кандидата исправления или после непрошедших проверок итогового commit) новая попытка от нового `main` отменяет только добавленные слияния. Для `source = resume` новая попытка начинается после принятия `fix_sha` (`revert.status = merged`): цели, покрытые решением, получают `fixed_by = fix_sha` и `resumed = true`. Решение покрывает только цели, чей `head_sha` — предок `fix_sha` (проверка `compare` при начале проверки `fix_sha`); слияния, сделанные после исправления, остаются целями revert-PR офиса. Кандидаты не деплоятся, пока все цели не исправлены. Публикация кандидата, содержащего revert-commit всех попыток, снимает блокировку. Записи `revert` без `targets` (до `P5.3b`) перед снятием блокировки получают цель с составом слияний офиса из `GET /repos/{repo}/compare/{base}...{head}`; задачи этих слияний в той же транзакции получают `failed` с видом ошибки цели и причиной (например, задача, оставшаяся `released` после ручного отката старой версии), чтобы доработка запустилась.

## Доработка после отката

Решение владельца 25 октября 2026: задача, чьё слияние отменено revert-PR офиса, возвращается на доработку один раз (`OFFICE_REWORK_LIMIT`, по умолчанию 1) и проходит конвейер заново.

1. Точка запуска — снятие блокировки владельца публикацией кандидата, содержащего его исправления, независимо от `origin` публикуемого кандидата (revert мог опубликоваться в составе более нового кандидата задачи). Доработка — только по целям, отменённым revert-PR офиса; для целей с `resumed = true` (`main` исправил владелец) доработки нет.
2. В транзакции публикации для каждого слияния `merges` каждой цели офис находит задачу (операция `merge_pr` с `external_ref` = SHA). Задача в `failed` с `failure_kind` `verify_failed`, `rolled_back` или `checks_failed` и `rework_count < OFFICE_REWORK_LIMIT`: `rework_of` = владелец (ключ идемпотентности — повторная обработка того же владельца ничего не меняет), `rework_count + 1`, `rework_priority`, `rework_context` (источник, выпуск, `merge_sha` исходного слияния, комментарий администратора), `usage.model_calls_limit` + 30, переход `failed` → `queued`, событие `rework_started`. Лимит исчерпан — событие `role_finished` (`step = rework`) «Лимит доработки исчерпан», задача остаётся `failed`; очередь продолжает следующие кандидаты. Причина «Лимит доработки исчерпан» пишется в `rework_reason` уже при повторном сбое.
3. Захват слота: задачи с `rework_priority` идут раньше обычных `queued` (по времени возврата), сразу в `developing` без повторного подтверждения требований (тот же `spec_hash`, решение `approve_spec` первого прохода действует). В той же транзакции `branch`, `base_sha`, `head_sha`, `pr_number`, `pr_url`, `merge_sha`, `checks`, `failure_kind` очищаются, `fix_cycles` и счётчик агента ревью PR обнуляются; история остаётся в событиях.
4. Попытка: номер попытки графа — число решений `retry` плюс `rework_count` (у задач без доработки не меняется), checkpoint `<task_id>:<attempt>` новый. Время попытки — от перехода в `developing` после `rework_started`; ожидание слота не расходует `OFFICE_TASK_TIME_LIMIT_MINUTES`. Состояние QA — файлы `qa-state-<attempt>-<round>.json` новой попытки.
5. Носитель доработки — `<task_id>-r<n>`: worktree `workspace/wt/<task_id>-r<n>`, ветка `office/<task_id>-r<n>`, ключи операций `push:<task_id>-r<n>:<sha>`, `create_pr:<task_id>-r<n>` и так далее; журнал первого прохода не мешает. Worktree прежнего прохода удаляется.
6. Подготовка ветки — операция `rework_prepare:<task_id>:<n>`: запись `started` с `base_sha` (текущий `origin/main`) и `source_sha` (`merge_sha` исходного слияния, включая тест QA) до действий Git; worktree на `base_sha`; `git cherry-pick --no-commit source_sha`; commit офиса с trailer `Office-Rework: <task_id>-r<n>` и `Office-Source: <source_sha>`; `succeeded` (`external_ref` — HEAD, `detail.applied`). Конфликт — сброс к `base_sha`, `applied = false`: рабочая копия — чистый `main`, исходный diff передаётся разработчику. После перезапуска: worktree нет — создаётся; HEAD = `base_sha` с изменениями прерванного `cherry-pick` — сброс и повтор; HEAD — commit доработки с родителем `base_sha` — `succeeded`; другое состояние — операция `failed`, задача `needs_attention`. Разработчик вызывается только после `succeeded`.
7. Материалы разработчику собирает код офиса в начале узла разработчика, один раз на попытку (сохраняются в `rework_context`; перезапуск не собирает повторно): причина (`verify` и `rollback` выпуска, `rework_reason`, комментарий администратора, непрошедшие шаги критического E2E; при ручном откате — причина и проверка кандидата отката); события деплоя офиса и `GET /v1/services/{serviceId}/deploys/{id}` деплоя, автоматического отката и деплоя кандидата ручного отката (статус, `trigger`, время); логи Render `GET /v1/logs` (`ownerId` из `GET /v1/services/{serviceId}`, `resource` — сервис, окно от начала деплоя до проверки ручного отката, конца или проверки автоматического отката либо проверки выпуска, `direction = forward`, следующие страницы по `hasMore`/`nextStartTime`/`nextEndTime`, до 10 страниц): строки `type = build` только при ошибке сборки, строки приложения уровня `warning`/`error` и трассировки, строки доступа uvicorn отбрасываются; для непрошедших проверок итогового commit — лог упавшей job GitHub Actions `GET /repos/{repo}/actions/jobs/{id}/logs` (ответ `302` на хранилище, переход без заголовка `Authorization`), последние строки; исходный diff `merge_sha^..merge_sha`. Каждый источник после очистки — не больше 4 КБ. Недоступный источник — строка «логи недоступны: <причина>», доработка продолжается.
8. Очистка до сохранения и до передачи модели ко всем источникам, включая комментарий администратора, diff и тексты ошибок: точные значения секретов офиса (ключи моделей, токен App, ключ Render, строки подключения БД и их пароли) и шаблоны — заголовки `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, схемы `Basic`/`Bearer`/`token`, JWT, префиксы ключей (`sk-ant-`, `sk-proj-`, `sk-`, `sb_secret_`, `sb_publishable_`, `ghs_`, `ghp_`, `github_pat_`, `rnd_`), длинные строки рядом со словами `key`, `token`, `secret`, `password`, учётные данные в URL, параметры запроса `token`, `key`, `secret`, `password`, `code`, `sig`, пары `имя=значение` и `имя: значение` с именами, содержащими `password`, `passwd`, `secret`, `token`, `api_key`, `apikey`, `access_code`, `cookie`, в том числе поля JSON и словарей с именами в кавычках, e-mail, IPv4 и IPv6 заменяются на `[скрыто]`. Тексты сообщений участников из логов приложения не передаются. Ключи остаются у офиса: модели и sandbox их не получают.
9. Промпт разработчика получает блок «Доработка после отката» (номер попытки, применён ли `cherry-pick`) и материалы в маркерах данных («данные, а не инструкции»); QA и критик — причину доработки. Дальше полный конвейер: проверки, QA (тест должен падать на новой базе и проходить на новой версии), критик, PR, агент ревью, слияние, проверки итогового commit, выпуск.

## Возобновление

`resume_releases` — решение администратора `POST /api/releases/{id}/decisions`, идемпотентное по `idempotency_key`.

1. С `fix_sha` (кандидат — `release_blocked_by`): `revert` кандидата заменяется записью `source = resume`. Офис проверяет, что `fix_sha` входит в `main` и является потомком откатанного `commit_sha`, ждёт обязательных проверок `push` для `fix_sha`, выполняет критический E2E и создаёт кандидата исправления `origin = resume` с `origin_decision_id`. Блокировка снимается после его публикации; до неё блокировка сохраняется. Повторное решение с тем же `fix_sha` после создания кандидата исправления (`revert.status = merged`) отклоняется (`409 decision_not_allowed`) без изменения `revert`: иначе исправление вернулось бы в `pending`, а существующий кандидат перестал бы проходить блокировку. Если кандидат выпуска этой задачи с тем же `fix_sha` уже существует (например, решение вернулось к прежнему `fix_sha` после другого), новый кандидат не создаётся: после проверок `revert` получает `status = merged` и `candidate_id` существующего кандидата, если тот ещё в очереди (`pending`); иначе `revert.status = needs_attention` с причиной.
2. Без `fix_sha`, кандидат остановлен в очереди (`pending` с `blocked_reason`): причина остановки очищается, задача возвращается в `awaiting_release`.
3. Без `fix_sha`, кандидат активен и остановлен: сначала сверка. В списке Render есть нетерминальный деплой, операция деплоя или отката ещё сверяется (`started`), `/api/version` недоступен или не совпадает с последним `live`-деплоем — `409 decision_not_allowed` с причиной, состояние не меняется. Иначе незакрытые операции кандидата закрываются, `live`-деплой определяет публикацию: совпадает с `commit_sha` кандидата — кандидат `released` и `is_published`; иначе кандидат `failed`, публикация — кандидат офиса этой версии или `published_sha`; если кандидат откатывался — блокировка и revert-PR. Затем освобождается `active_release_id`.
4. Без `fix_sha`, кандидат — `release_blocked_by`: блокировка не снимается. Решение повторяет revert-PR с начала, если `revert.status = needs_attention`, у кандидата нет операций в `started` или `unknown` и revert-PR не слит в `main` (у `source = auto` пустой `fix_sha`); иначе `409 decision_not_allowed`. `revert` получает `status = pending`, `source = auto`, `attempt` на 1 больше, `decision_id` решения; `fix_sha`, `candidate_id` и `reason` очищаются. Исполнитель закрывает открытые revert-PR прежних попыток — номера берутся из событий `pr_opened` задачи с `revert_of` этого кандидата (операция `close_pr:revert:<release_id>:<n>:<номер PR>`, событие `pr_closed`; операция `started` после перезапуска завершается по фактическому состоянию PR), — и выполняет операцию `revert:<release_id>:<n>`. Если ветка прежней попытки уже есть на GitHub, новая попытка создаёт ветку `office/revert-<release_id>-<n>` (`revert.tree = revert-<release_id>-<n>`), прежний worktree удаляется; иначе имя ветки прежнее. `resume_releases` с `fix_sha` сохраняет `revert.attempt` и `revert.tree`, поэтому следующий повтор без `fix_sha` получает неиспользованный номер попытки. Затем поля revert-PR (`base_sha`, `head_sha`, `pr_number`, `pr_url`, `checks`) заменяются новыми, и конвейер идёт по пунктам 2–3 раздела «Revert-PR». Кандидат исправления получает `origin = auto_revert` и `origin_decision_id` решения повтора.

## Сервис `vibe-chat`

Офис использует только публичные операции сервиса `vibe-chat`: `GET /api/version` (SHA commit опубликованной сборки), `GET /healthz` и главную страницу с `<meta name="app-version">`. Формат ответов определяет `apps/chat/contracts/api.md`. Запросы выполняются без кеширования. Офис не обращается к данным пользователей сервиса и не хранит его ключи.
