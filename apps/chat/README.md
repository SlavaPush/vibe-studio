# vibe-chat

Публичный AI-чат: отдельные диалоги для каждого участника, проверка каждого сообщения модерацией и классификатором риска, маршрутизация запроса по намерению и сложности на подходящую модель и уровень усилий, генерация изображений, постоянная история.

Облачные модели: Anthropic (основной провайдер), OpenAI (резервный, а также модерация и изображения). Сервис развивает мультиагентный офис из репозитория [back-office](https://github.com/SlavaPush/back-office).

## Состав

| Каталог | Назначение |
| --- | --- |
| `api/` | FastAPI: сеансы, диалоги, задания, шлюз входа, маршрутизация, провайдеры, SSE |
| `web/` | React + TypeScript + Vite: интерфейс чата |
| `contracts/api.md` | Контракт API между `web/` и `api/`: операции, события, ошибки, перечисления и проверяемые примеры |
| `infra/` | `docker-compose.yml` с локальной PostgreSQL; `Dockerfile` образа для Render (интерфейс и API в одном образе) |

Статус:

- `P2` — гостевые сеансы, диалоги и история в PostgreSQL, задания и события SSE, шлюз входа (OpenAI Moderation и классификатор, fail-closed), маршрутизация по намерению и сложности, fallback между провайдерами, генерация изображений с хранением в приватном Supabase Storage, лимиты и резерв бюджета. Интерфейс работает с реальным API.
- `P3` — опубликован: https://vibe-chat-nwvw.onrender.com. Образ Docker, конфигурация публичного окружения, уведомление открытой вкладки о новой версии; порядок деплоя — раздел «Деплой на Render».
- Коды доступа — индивидуальные коды участников, отзыв отдельного кода, квота по коду; раздел «Коды доступа». Публичная проверка выполняется после деплоя.

## Запуск локально

Требования: Python 3.12 и [uv](https://docs.astral.sh/uv/), Node 24, Docker.

1. Создать `.env` и заполнить ключи. Файл `.env` не попадает в Git.

   ```bash
   cp .env.example .env
   ```

2. Запустить PostgreSQL (адрес совпадает с `DATABASE_URL` из `.env.example`):

   ```bash
   docker compose -f infra/docker-compose.yml up -d
   ```

3. Запустить API на порту `8001`. Схема БД применяется при старте.

   ```bash
   cd api && uv sync && uv run uvicorn app.main:app --reload --port 8001
   ```

4. Запустить интерфейс. Vite передаёт `/api` и `/healthz` на `http://127.0.0.1:8001`; другой адрес задаётся переменной `API_PROXY_TARGET`.

   ```bash
   cd web && npm ci && npm run dev
   ```

5. Создать код доступа (раздел «Коды доступа») и открыть `http://localhost:5173`.

Cookie сеанса по умолчанию имеет флаг `Secure`. Chrome принимает такую cookie на `http://localhost`, Safari может не принять. Для Safari запустить API с `COOKIE_SECURE=false` в окружении.

## Проверки на реальных API (платные вызовы)

Шлюз входа на 26 эталонных запросах (`api/tests/data/gateway_cases.json`): реальные модерация и классификатор без основной модели. Код возврата `1` при расхождении решения «пропустить/отклонить» хотя бы в одном случае. Совпадение `intent` и `complexity` выводится долей.

```bash
cd api && uv run python scripts/eval_gateway.py
```

Сквозная проверка через HTTP к запущенному API: два пользователя, простой и сложный запрос, изображение при выбранной текстовой модели, запрещённый запрос, попытка получить системный промпт, изоляция пользователей, повтор с тем же ключом идемпотентности. Значение `--origin` должно входить в `ALLOWED_ORIGINS` сервера. Тот же скрипт используется для публичного адреса на этапе `P3`.

Скрипту нужен действующий код доступа: переменная окружения `VIBE_ACCESS_CODE` или параметр `--code`.

```bash
cd api && VIBE_ACCESS_CODE=<код> uv run python scripts/smoke_chat.py --base-url http://127.0.0.1:8001 --origin http://localhost:5173
```

Фактические модели и уровни усилий видны в выводе скрипта и в таблице `attempts`:

```bash
docker compose -f infra/docker-compose.yml exec postgres psql -U vibe -c "SELECT purpose, model, effort, status FROM attempts ORDER BY created_at DESC LIMIT 20"
```

Smoke-проверка облачных моделей (флаг `--image` добавляет генерацию одного изображения):

```bash
cd api && uv run python scripts/smoke_models.py
```

Smoke-проверка приватного Supabase Storage (bucket, загрузка, подписанная ссылка, запрет прямого доступа, удаление):

```bash
cd api && uv run python scripts/smoke_storage.py
```

## Коды доступа

Каждый участник входит по своему коду. Коды создаёт и отзывает владелец скриптом `api/scripts/access_codes.py` на своей машине; в публичном сервисе нет API для управления кодами. Скрипт в образ Docker не входит.

- В таблице `access_codes` хранятся метка участника, SHA-256 кода, время создания и отзыва. Сам код в БД не хранится и печатается один раз, при создании.
- Код — 12 символов из строчных латинских букв и цифр без похожих символов (`0`, `o`, `1`, `l`, `i`), выводится группами `xxxx-xxxx-xxxx`. При входе регистр, пробелы и дефисы не учитываются.
- Каждый вход создаёт нового гостевого пользователя, связанного с кодом. Квота участника считается по всем пользователям кода.
- Отзыв действует сразу, без перезапуска сервиса: все сеансы кода получают `401`, открытый поток событий закрывается, повторный вход кодом невозможен. Подписанная ссылка на файл, выданная до отзыва, действует до 10 минут. Уже выполняющееся задание завершается и учитывается в квоте.
- Сеансы, созданные по общему коду `DEMO_ACCESS_CODE` до этого изменения, недействительны.

Команды выполняются из каталога `api`. Строка подключения берётся из переменной `DATABASE_URL` (окружение, затем `../.env`); параметр `--database-url-env` задаёт другую переменную. Значение строки подключения не печатается. Перед работой скрипт применяет `schema.sql`, как сервер при старте.

```bash
uv run python scripts/access_codes.py add alice
uv run python scripts/access_codes.py list
uv run python scripts/access_codes.py revoke alice
```

Для Supabase (строка в `DATABASE_URL_SUPABASE` из `.env`):

```bash
uv run python scripts/access_codes.py --database-url-env DATABASE_URL_SUPABASE add alice
```

`add` печатает метку и код; повторная метка — ошибка. `list` печатает для каждого кода метку, время создания и отзыва, число пользователей и действующих сеансов, число заданий и изображений за 24 часа; коды не печатаются. `revoke` отмечает код отозванным; повторный отзыв сообщает, что код уже отозван. Вывод — строки JSON.

## Пределы демоверсии

- История привязана к cookie сеанса. После удаления cookie или на другом устройстве история недоступна; восстановления нет.
- Лимиты за скользящие 24 часа (значения по умолчанию, переменные в `.env.example`):

  | Единица | Участник (код доступа) | Источник запросов | Сервис |
  | --- | --- | --- | --- |
  | Задания | 60 | 300 | 1500 |
  | Изображения | 5 | 25 | 100 |
  | Токены (вход + выход) | 1 000 000 | 5 000 000 | 20 000 000 |

  Предел участника считается по всем сеансам его кода доступа: новый вход с тем же кодом его не сбрасывает. Переменные предела участника сохраняют префикс `USER_`. Источник запросов — HMAC адреса клиента. Новая гостевая сессия с того же адреса не сбрасывает предел источника. Дополнительно: одно активное задание на пользователя, не больше 8 платных попыток на задание, 20 новых сеансов в час с одного адреса.
- Перед каждым платным вызовом резервируется верхняя граница расхода: входные токены не больше числа байтов UTF-8 запроса плюс 32 на сообщение, выходные — переданный провайдеру предел. Выходные токены генерации изображения в токенную квоту не входят: расход генерации ограничивает квота изображений.
- Неизвестный исход платного вызова (таймаут, обрыв, HTTP 5xx) не повторяется автоматически. Пользователь видит ошибку и может отправить запрос заново.

## Образ Docker

`infra/Dockerfile` собирает интерфейс (`node:24.22.1-slim`) и запускает API (`python:3.12.15-slim`, зависимости через `uv 0.12.23` без dev-группы). FastAPI раздаёт сборку интерфейса из `/srv/web`:

- `/assets/*` — файлы сборки с заголовком `Cache-Control: public, max-age=31536000, immutable`;
- файлы корня сборки (`favicon.svg`) — по списку, составленному при старте;
- любой другой `GET`, кроме `/api/...` и `/healthz`, — `index.html` с `Cache-Control: no-cache` и версией сервера в `<meta name="app-version">`;
- неизвестный путь `/api/...` — `404` с `ApiError`.

Процесс работает под пользователем с UID `10001`, файлы приложения принадлежат root и доступны только на чтение. В образ попадают только `api/app/`, зависимости и сборка интерфейса: `.dockerignore` исключает всё остальное, включая `.env`, тесты и скрипты. Uvicorn запускается с `--no-proxy-headers`: адрес клиента определяет приложение (`TRUST_PROXY_HEADERS`, `CLIENT_IP_SOURCE`, `PROXY_HOPS`). После `SIGTERM` Uvicorn ждёт открытые соединения не больше 3 с, исполнитель ждёт активные задания до 15 с и ещё до 5 с после их отмены. Задание, которое не успело сохранить состояние, следующий экземпляр завершает по правилам восстановления без повторного платного вызова.

Проверка образа с локальной PostgreSQL (порт `8000` на машине владельца занят, поэтому `18080`):

```bash
docker compose -f infra/docker-compose.yml up -d
docker run --rm -p 127.0.0.1:18080:10000 \
  -e DATABASE_URL=postgresql://vibe:vibe@host.docker.internal:5432/vibe \
  vibe-chat:local
curl http://127.0.0.1:18080/healthz
```

Ответы содержат заголовки безопасности: `Content-Security-Policy` (скрипты только с того же origin, изображения также из `SUPABASE_URL`, запрет встраивания во фреймы), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`.

## Деплой на Render

Сервис создаётся вручную (Render MCP или Dashboard); `render.yaml` в репозитории нет. Параметры web service:

| Параметр | Значение |
| --- | --- |
| Репозиторий и ветка | `SlavaPush/vibe-chat`, `main` |
| Среда | Docker, Dockerfile `infra/Dockerfile`, контекст — корень репозитория |
| Регион | Singapore (ближе всего к Supabase `ap-south-1`) |
| Тариф | Free |
| Health check | `/healthz` |
| Автодеплой | выключен: деплой запускается вручную |

Переменные окружения. Секретные значения владелец вводит в Render Dashboard; в репозиторий и в сообщения они не попадают.

| Переменная | Значение | Секрет |
| --- | --- | --- |
| `DATABASE_URL` | строка Supabase session pooler: порт `5432`, `sslmode=require` | да |
| `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` | ключи провайдеров | да |
| `SUPABASE_SECRET_KEY` | секретный ключ Storage | да |
| `QUOTA_SALT` | случайная строка для HMAC адреса клиента | да |
| `SUPABASE_URL` | адрес проекта Supabase | нет |
| `SUPABASE_STORAGE_BUCKET` | `images` | нет |
| `TRUST_PROXY_HEADERS` | `true` | нет |
| `PROXY_HOPS` | `1`; при `CLIENT_IP_SOURCE=cf-connecting-ip` не используется | нет |
| `CLIENT_IP_SOURCE` | `cf-connecting-ip`; выбран по диагностическому журналу (см. ниже) | нет |
| `LOG_FORWARDED_CHAIN` | `false`; `true` только на время диагностики | нет |

Render сам задаёт `RENDER=true`, `PORT`, `RENDER_GIT_COMMIT` и `RENDER_EXTERNAL_URL`. Из них сервер берёт порт, версию (первые 7 символов commit) и разрешённый `Origin` (если `ALLOWED_ORIGINS` не задана). При `RENDER=true` сервер не стартует, если пуста хотя бы одна переменная из `QUOTA_SALT`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `DATABASE_URL`, если `COOKIE_SECURE=false` или если `DATABASE_URL` указывает на `localhost`, `127.0.0.1`, `::1` либо не содержит хоста. В журнале деплоя указываются имена переменных без значений. Переменная `DEMO_ACCESS_CODE` больше не используется: вход выполняется по индивидуальным кодам (раздел «Коды доступа»).

Ограничения тарифа Free: сервис засыпает после 15 минут без запросов, первый запрос после сна ждёт холодного старта около минуты, память — 512 MB. Перед демонстрацией открыть URL заранее. Задание, выполнявшееся в момент засыпания, завершается по правилам восстановления.

Проверка после деплоя:

1. `GET https://<сервис>.onrender.com/healthz` возвращает `{"status":"ok"}`, `GET /api/version` — первые 7 символов commit.
2. Сквозная проверка (платные вызовы):

   ```bash
   cd api && VIBE_ACCESS_CODE=<код> uv run python scripts/smoke_chat.py --base-url https://<сервис>.onrender.com --origin https://<сервис>.onrender.com
   ```

3. Открытая вкладка после следующего деплоя показывает «Доступна новая версия»; страница не перезагружается сама, черновик сообщения восстанавливается после обновления.

### Выбор источника адреса клиента

Лимиты источника и новых сеансов считаются по HMAC адреса клиента. При `TRUST_PROXY_HEADERS=true` адрес берётся по `CLIENT_IP_SOURCE`:

- `xff_from_end` — элемент `X-Forwarded-For` с номером `PROXY_HOPS` с конца;
- `xff_first` — первый элемент `X-Forwarded-For`;
- `true-client-ip`, `cf-connecting-ip`, `x-real-ip` — значение одноимённого заголовка.

Если заголовка нет или значение не является IP-адресом, используется адрес соединения. Неизвестное значение `CLIENT_IP_SOURCE` останавливает запуск сервера.

Порядок выбора:

1. Задать `LOG_FORWARDED_CHAIN=true` и выполнить деплой.
2. С одной машины отправить несколько запросов входа с неверным кодом, без поддельного заголовка и с ним:

   ```bash
   URL=https://<сервис>.onrender.com
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "$URL/api/demo-session" \
     -H "Origin: $URL" -H 'Content-Type: application/json' -d '{"code":"wrong"}'
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "$URL/api/demo-session" \
     -H "Origin: $URL" -H 'Content-Type: application/json' -H 'X-Forwarded-For: 198.51.100.1' -d '{"code":"wrong"}'
   ```

3. В журнале Render найти строки `forwarded chain`. В строке: `count` — число элементов `X-Forwarded-For`, `xff` — первые 8 символов HMAC каждого элемента, `headers` — имена присутствующих заголовков из набора `x-forwarded-for`, `x-real-ip`, `true-client-ip`, `cf-connecting-ip`, `forwarded`, `values` — хеши значений остальных заголовков, `source` — хеш выбранного сейчас адреса. Адреса в журнал не попадают.
4. Выбрать источник, хеш которого одинаков во всех запросах с машины и не совпадает с хешем поддельного `198.51.100.1`. Пример: если первый элемент `xff` постоянен, а поддельный адрес появляется вторым, нужен `xff_first`. Если постоянен хеш в `values` для `true-client-ip`, нужен `true-client-ip`.
5. Задать `CLIENT_IP_SOURCE`, вернуть `LOG_FORWARDED_CHAIN=false`, выполнить деплой.
6. Проверка: 21 запрос входа с неверным кодом с одной машины, половина с разными поддельными `X-Forwarded-For`. Начиная с 21-го запроса сервер отвечает `429` (предел — 20 новых сеансов в час с одного адреса). С другой машины вход в это время работает.

Откат: Dashboard → сервис → Events → Rollback на предыдущий деплой или ручной деплой предыдущего commit. Данные хранятся в Supabase (PostgreSQL и Storage) и не зависят от версии образа. Схема применяется при старте и не удаляет данные.
